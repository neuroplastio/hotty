- **The focused element goes away: focus fixup, as in HTML** (2026-11-17;
  from hotty-surf's L2 display review: a closing toast's button,
  and Basecoat's toast.js blurring by hand).
  - **Today:** §10.1 never says what happens when the focused element
    leaves the document, or stops taking focus (disabled, hidden, not
    rendered, inert). Neither does HOST.md. Hosts may differ. The cells
    renderer already drops focus with no `blur` (hotty-surf L1: "a
    disabled or hidden field loses the keyboard … with no blur").
  - **Nothing in the spec gives "nothing focused" on request:** `a=focus`
    without `t` keeps the focused element or focuses the first one.
    `a=blur` gives the keyboard back to the terminal. A page's
    `activeElement.blur()` keeps the keyboard in the page with nothing
    focused; hotty has no counterpart.
  - **The reviewer's proposed wording (§10.1):** "When the focused element
    leaves the document, or stops taking focus (disabled, hidden, not
    rendered, inert), it loses focus. The surface keeps the keyboard with
    nothing focused, and the host sends no `blur`. Keys then reach the
    program (§10.2, *Keys for the program*)."
  - **With it, the kit needs no blur API:** a closing toast's buttons
    are written `disabled` from the frame it closes in, and a popover's
    `invisible` drops focus as a browser's does. hotty-surf makes
    `Autofocus(ctx, "")` a fault meanwhile, and adds `surf.Blur` (meaning
    `a=blur`) only if a component ever has to hand the keyboard to the
    terminal.
  - **Leans taken** (2026-11-17, under the maintainer's rule that day,
    "nothing waiting for my approval, take the leans", relayed by gov).
    The reviewer's wording goes into §10.1 when 0.9 is drafted, with
    these answers:
    - **The program is told nothing,** as HTML's focus fixup fires no
      event. A program that removes or disables the element knows it did.
      For one hidden by layout alone, the next key goes to the program
      (§10.2), which shows it nothing is focused.
    - **When the check runs:** each time the host lays the document out,
      after the program's changes and after a resize, as a browser
      runs focus fixup when it updates the rendering.
    - **`opacity: 0` doesn't count,** nor does anything else that leaves
      the element rendered and focusable in a browser. `visibility:
      hidden`, `display: none`, `disabled`, `inert` and leaving the
      document do count.
  - **Drafted** (2026-11-22, on `hotty-0.9`, revised after the blind
    review): SPEC §9, §10.1, §16 and Appendix B, SDK.md §4.4, the vectors
    and their README. For the

- **`data-keys` is the element's own; `data-keys-tree` inherits**
  (2026-11-22; the maintainer, from hotty-surf's edit-shortcut keymaps,
  where an edit group can't go on a container and is written on every
  field instead).
  - **Today (§10.2, §10.5, §11):** every `data-keys` reaches every focused
    element inside it, of every kind, and a document selection's copy reads
    the same chain. So a binding leaks where it doesn't belong:
    - `ctrl+c=copy` on a container also copies a document selection on
      a Mac, where Ctrl+C should interrupt;
    - a list's `space=program` reaches its buttons and fields, each of
      which then needs `space=default`;
    - the edit shortcuts go on each field, about 200 B a field (20 KB on
      a table of 100 editable cells).

    A field also leaves scroll actions out under a rule of its own.
  - **Inheritance is still needed for some cases:**
    - a leader or prefix (`mod+k` anywhere in a view);
    - a list whose rows take focus, with its arrows on the list;
    - a pager's `j` and `k` while a link inside it is focused;
    - a pane's shortcuts from any field or button in it.

    So it becomes opt-in, not dropped.
  - **The shape:**
    - **`data-keys`** is the element's own. It applies only while that
      element has focus.
    - **`data-keys-tree`** applies while focus is on the element or
      anything inside it. Its syntax is the same as `data-keys`. It is an
      attribute of its own, not a marker inside `data-keys`, because key
      names already use `+`, and because one value then carries one scope
      and a delta changes one scope.
    - **A focused element's keymap** is built in three steps. It starts
      from the default keymap, for a text field only. Then comes
      `data-keys-tree` from the root down to the element, its own
      included, with the nearer element winning key by key, as today.
      Last comes the element's own `data-keys`, which wins. In its own
      `data-keys`, `key=default` cuts off an inherited binding, and that
      is `default`'s only use.
    - **The document's keymap** is the root's own `data-keys`. It applies
      with nothing focused, and §11's selection copy reads it. Tree
      bindings never apply to a selection.
    - **One rule for every reader:** a reader ignores a binding whose
      action it does not take, as if it were not there, so the binding
      neither acts nor overrides. This replaces two rules: a field leaving
      scroll actions out, and other elements letting editing actions
      override and then do nothing.
  - **What it gives:**
    - The edit shortcuts go on the root once, as tree. Fields take them,
      buttons ignore them, and a selection doesn't see them, so the Mac's
      Ctrl+C still interrupts.
    - A list's keys are its own, so its buttons keep Space without a
      give-back.
    - A pager's tree `j` scrolls from a link and types in a field.
  - **No per-context attributes** (field, focus, selection). Weighed and
    not needed with the above.
  - **The gap left:** a tree binding to `program` or `prefix` of a key a
    field also uses still reaches the field, such as a scope forwarding
    `j` with a search field inside it. The field cuts it with its own
    `j=default`, and hotty-surf can write that cut itself. If a blind
    review or plx's measurement finds many such cuts, add a field-only
    tree attribute then.
  - **Compatibility:** none (the maintainer). Documents that rely on
    inheritance through `data-keys` change meaning, and programs and
    hosts negotiate 0.9 under §15.
  - **What changes outside the spec:**
    - every host's root-down walk: hotty-blitz, xterm-addon-hotty, and
      hotty-surf's cells;
    - `hotty.Resolve` in hotty-go, and its counterparts in hotty-ts,
      hotty-rs and hotty-lua;
    - hotty-surf's writer, where `KeyScope`, prefixes and groups bound
      on a root become tree, and the rest own;
    - hotty-a2ui (paused) and the web/hotty demos.

    plx writes no `data-keys` of its own, so it only follows hotty-surf.
  - Before drafting: a blind review of the shape. Then measure plx's
    longest list under its KeyScope and leader, in bytes and deltas,
    before and after.
  - **Reviewed and measured** (2026-11-22). The review read the shape
    against §10.1–10.7 and §11. The measurement compared hotty-surf's
    writer as it stands with a spike that writes own and tree, on plx's
    views. Each pair was checked to give every focusable element the same
    keymap, key by key:
    - **nav**, 31 rows under its KeyScope, plx's leader and the editing
      keymaps: 4,216 B of `data-keys` becomes 1,184 B. A change of the
      leader goes from 31 attribute operations (4,276 B of msgpack) to one
      (142 B), and so does a change of one of the scope's bindings.
    - **settings:** 1,759 B becomes 1,201 B. With cocoa's edit shortcuts
      on Linux, 2,563 B becomes 1,204 B: 228 B a text field today, but
      only where the shortcuts differ from the host's.
    - **The gap: 0 cuts in plx.** No KeyScope holds a field, and
      hotty-surf's writer already keeps printable keys off fields. Fix 3
      below makes that the reader's rule, so no field-only attribute.
    - **What inherits today** is one thing: the editing keymaps on a
      wrapper, read by every text field. KeyScopes are written on each
      control, and the kit's containers declare no keys.

    The fixes taken into the draft (hotty Agent):
    1. With nothing focused, the keymap is the body's: its
       `data-keys-tree`, then its own `data-keys`. As the shape stood, a
       leader or a list's arrows on the root stopped at focus fixup.
    2. What each reader takes, in a table. `program`, `prefix` and
       `default` are overrides for every reader, a selection's included,
       or §11's `mod+c=program` would copy. A selection's keymap starts
       from the default keymap.
    3. A text field takes no `data-keys-tree` binding to `program` or
       `prefix` of a key it types; its own `data-keys` gives one.

    The review's writer notes went into the legs (hotty-surf), and its

### Focus fixup: the wording

Revised after the blind review (2026-11-22): an edit commits with
`change`, as HTML's fixup does; no `blur` for hotty's own reason; the
fixup comes before the next key; "stops taking focus" defined; HTML's
first-`legend` exception; and the sentences that misstated HTML or what a
program learns are gone.

SPEC.md §10.1, a bullet after **A click elsewhere gives the keyboard
back** (its last bullet, *With nothing focused*, as the own-and-tree
keymaps item has it):

```
- **The focused element goes away.** When the focused element leaves the
  document, or stops taking focus, it loses focus, as in HTML's focus
  fixup. The surface keeps the keyboard with nothing focused (§10.2).
  - **Leaving the document:** a delta removes it or what holds it (§6),
    or a new document replaces the one it was in (§5.1).
  - **Stopping taking focus:**
    - **No longer focusable:** it is none of the elements that take focus
      (above) and has no `tabindex`: a link whose `href` is removed, an
      editing host no longer `contenteditable`, an element whose `tabindex`
      is removed. An element with a `tabindex` that parses as an integer, of
      any value, is focusable, so a focused one whose `tabindex` goes from 0
      to -1 keeps focus, and so does one with `tabindex=-1` that `a=focus`
      gave focus, though no click would.
    - **Disabled,** as HTML has it: its own `disabled`, or a disabled
      `fieldset`'s, unless it is inside that fieldset's first `legend`.
    - **Inert:** made `inert`, or inside an element made `inert`.
    - **Not rendered:** `display: none`, its own or an ancestor's, which
      a `hidden` attribute gives too; inside an element whose content is
      skipped (`content-visibility: hidden`, a closed `details`); or
      `visibility: hidden`, which browsers refuse focus though HTML counts
      it rendered.

    `opacity: 0` does not count, nor does anything else that leaves the
    element rendered and focusable in a browser: scrolled out of view,
    clipped, covered, or outside the placement's window (§5.2).
  - **When:** a delta or a document that removes the focused element, or
    makes it disabled, inert or no longer focusable, takes effect before
    the next key or pointer event the surface is offered. What CSS hides
    takes effect at the next layout, which the host runs before it offers
    the next key; a resize lays the document out again.
  - **No `blur`, no `focus`.** The surface keeps the keyboard, which is
    what `blur` would deny, and no element was focused. A text control
    the user changed commits it as focus leaving it does (§9), with its
    `change`, as HTML's fixup does for an element still in the document;
    one removed sends nothing. A program that removed or disabled the
    element knows it did. One whose element layout alone hid is not told,
    and the last `focus` it heard (§10.2, *Keys for the program*) is then
    stale.
  - **With nothing focused,** the keymap is the `body`'s (§10.2, *Keymaps*):
    a key it gives the program, or binds to a scroll action, does that, and
    every other key but a scrolling document's own scrolling keys (§5.3)
    reaches the program. `tab` focuses the first of the elements that take
    focus (above), as `a=focus` without `t` does, and `shift+tab` the last;
    with none, the surface loses the keyboard, as past the last (§10.2). A
    prefix (§10.5) goes on, since the surface kept the keyboard, and so does
    one the body's keymap starts.
```

SPEC.md §10.1, **With `t`** (its last sentence is new) and **Without
`t`**, which now reads "the first of the elements that take focus
(below)":

```
- **With `t`:** the element is focused (`ENOTARGET` if there is none). A
  text field keeps its selection (§10.2). An element that is not
  focusable (below: it takes no focus and has no `tabindex`), or is
  disabled, inert or not rendered, is not focused, and that is no error:
  the surface takes the keyboard, and an element that had focus keeps
  it, as HTML's `focus()` leaves it; with none, nothing is focused.
- **Without `t`:** the surface's focused element keeps focus, or else the
  first of the elements that take focus (below) receives it.
```

SPEC.md §9, the `change` row: focus leaving a text control commits it
"(including when the surface loses the keyboard, and focus fixup,
§10.1)".

SPEC.md Appendix B, a bullet before **Why scrolling keys**:

```
- **Why focus fixup sends no `blur`.** A component that closes, such as a
  toast whose button had focus, disables or hides what it shows, and the
  host has to do something with the focus it held. HTML is silent when the
  element is removed, and fires the element's `blur` (and a `change` for
  an edit) when it is hidden or disabled. hotty has no element blur: its
  `blur` says the terminal has the keyboard, which it does not, and a
  `focus` on another element would move the user where neither they nor
  the program went. So the host sends neither, and commits an edit as
  HTML does, so that no media query loses what the user typed.
  - **No event for layout alone.** A program that removed or disabled the
    element knows it did. One that hides its focused element with a media
    query is not told, and its last `focus` is stale. That is rare, and
    such a program can avoid it, so it costs no event.
  - **No blur of its own.** With fixup, a program that wants nothing
    focused disables or hides the element, as a page does, so hotty needs
    no counterpart of a page's `activeElement.blur()`. `a=blur` still
    gives the keyboard to the terminal.
  - **Before the next key,** because a program's delta and the user's
    next key race, and a key that reached the element the program had
    just disabled would be lost. What CSS hides is known only after
    layout, so the host lays out before it offers a key.
  - **Tab from nothing focused** goes to the first of the elements that take
    focus (§10.1), as `a=focus` without `t` does, and Shift+Tab to the last.
    A browser goes on from where the element was (its focus navigation
    starting point), but HTML says nothing of a starting point that was
    removed, and browsers differ there; the first and the last are one rule
    for every host.
```

SPEC.md §10.2, **`tab` and `shift+tab`**, move "between the elements of
the surface that take focus (§10.1)", and Appendix B's *Tab from nothing
focused* names the same list: "focusable", which now takes in
`tabindex=-1`, is left to what fixup and `a=focus` test (after the
verify, 2026-11-22).

SPEC.md §16: the vectors check "focus fixup".

SDK.md §4.4, the test host:

```
  `drop` in its `data-on`. It keeps the focused element, and drops focus
  as SPEC.md §10.1 has a host do when the element goes away, sending only
  the `change` of a field the user edited that is still in the document:
  when a delta or a document removes it; makes it disabled, by its own
  `disabled` or a disabled fieldset's, outside that fieldset's first
  `legend`; makes it or an ancestor `inert` or `hidden`; or removes what
  made it focusable, a `tabindex`, an `href` or `contenteditable`. What
  CSS hides it cannot see.
```

It skips the vectors marked `layout`, a new name in conformance/README.md
for what only a host that resolves CSS can see.

Four vectors, after "there is one keyboard":
- removed, disabled, a `tabindex` taken away, and a new document: an
  edited field still in the document sends `change`, a removed one
  nothing; `tab` from nothing goes to the first element (`a`, not `c`,
  which follows the removed `b`), `shift+tab` to the last; a `tabindex`
  that goes to -1 keeps focus, and so does `a=focus` on a `tabindex=-1`
  element until the `tabindex` is removed;
- a disabled fieldset, with a button in its first `legend` that takes focus,
  clicks on Enter, and keeps focus; an ancestor made `inert`; a `hidden`
  attribute; then `shift+tab` with none left sends `blur`;
- `a=focus` with `t` on a `div` and on a disabled field: no error; from
  nothing focused the surface takes the keyboard and Tab goes to the
  first element, and a focused field keeps focus and types on;
- `layout`: `display: none` from a class, its own and an ancestor's,
  `visibility: hidden`, a `details` closed, and a media query a resize
  turns on, each committing with `change`; `opacity: 0` keeps focus.

**Beyond the leans**, for the maintainer to look at:
- **`change` on fixup**, where the lean said "the program is told
  nothing". HTML's fixup on rendering fires `blur` and a `change` for an

### An identical resend: the wording

Revised after the blind review (2026-11-22): the MUST NOT covers anything
shown, not only an animated image; "type as sent" and "after reassembly";
and a vector step for the same bytes under another type.

SPEC.md §7.1, under **Updates**:

```
  - **The same again.** A resend whose id, type as sent and bytes, after
    reassembly (§3.4), match the stored resource changes nothing, and a
    host **MAY** ignore it: it draws nothing again, and is answered as any
    `a=res`. A type is compared as a string, so `text/css` and `text/css;
    charset=utf-8` differ. Ignored or not, it **MUST NOT** change what is
    shown: an animated image, a CSS animation or a transition goes on
    from where it is, scroll offsets stay, and no frame is drawn without
    the resource, such as one without the stylesheet or in a fallback
    font.
```

SPEC.md §7.1, a bullet after **References** (new, so the other-type step
has something to stand on):

```
- **Its type** says what it is, as a server's `Content-Type` does: a
  stylesheet link or `@import` applies a resource whose type, ignoring
  case and parameters, is `text/css`, and nothing else, as a browser does
  in a page in standards mode.
```

SPEC.md Appendix B, a bullet before **Why hide**:

```
- **Why an identical resend may change nothing.** A program that keeps
  no record of what the host holds, such as a multiplexer switching tabs,
  sends its stylesheet again, and each surface that links it is styled
  again for the same bytes. A host that compares them first skips that
  work, and the program sees no difference: the same bytes draw the same
  pixels. A redraw that reloads can change what is shown (an animation
  starting again, a frame without the stylesheet, offsets clamped while
  it loads), so that is ruled out whether the host compares or not.
- **Why other buttons, by number.** A browser closes a tab on a middle
  click, and a mouse's back and forward buttons go back and forward
  through a history. A surface took only the primary and the secondary
  buttons, so a program could offer neither: a middle press over a
  surface was the terminal's.
  - **One word for every button,** not one for each. The secondary press
    has a word for its meaning, because several devices make it: a mouse,
    a pen, Control on macOS, a long touch. No other button is made by more
    than one. The middle button has no touch or pen form. What a platform
    makes one of, such as Linux's three-finger tap on a touchpad, is one as
    far as a program can tell. Back's and forward's other forms, a
    touchpad's swipes, are scrolls here (§9). A word for each button would
    also need a new version for each. So `aux` takes them all, `button`
    says which as the DOM numbers them, and a later button needs nothing
    new: a program ignores one it does not use.
  - **A press, then `auxclick`.** These buttons act on their release: a
    browser closes a tab when the middle button comes up over it, so a
    user who moves off first cancels. A menu opens on the press, which is
    why the secondary press has no release. The press still comes first,
    with a secondary press's detail, for a program that acts at once, and
    as the place a drag of another button would begin if one is ever
    added.
  - **`auxclick`, not `click`.** `click` is activation, which a key makes
    too, and every handler of it would have to check the button: the trap
    the DOM added `auxclick` to avoid. Its detail is a click's, with the
    button and the cell. Unlike the DOM's, it never comes for the
    secondary button, whose press does nothing else.
  - **One button at a time,** and no `buttons` field. hotty has no gesture
    of two buttons, and no move is reported while one is held. A button
    pressed by chance during a drag should neither end the drag nor reach
    the program. A field can be added if chords are ever wanted.
  - **The terminal keeps the rest.** A middle press nobody asked for pastes
    the primary selection on Linux, as it always has over the cells, and
    `p` brings only the primary button, so a surface that asks for presses
    takes nothing from the user. A text field pastes as a browser's does,
    and an `aux` around it leaves it that: a tab's rename field pastes, and
    does not close the tab.
  - **Shift for every button but the primary,** as for the secondary press:
    one rule, though Shift with back or forward does little in a terminal.
  - **A host reports only what it can take whole.** A browser cancels the
    back button's navigation only in some engines, and only on the
    release. A press the program heard while the page went back would be
    worse than none.
  - **Room for touch and pens:** `button` means the same on every device,
    as in Pointer Events. A touch makes 0, and its long press 2; a pen
    makes 0 and 2, and its eraser would be 5. A later field naming the
    device needs no change to it.
```

One vector, after "a resource that arrives late": a resend of the same
id, type and bytes answers `ok` and a placement with `f=1` hears nothing;
other bytes replace it and are heard; the same bytes as `text/plain`
replace it too, the stylesheet stops applying, and `fit` gives `r: 1`. It

Nothing in SDK.md: the wire is unchanged, and the test host keeps

**Beyond the lean:**

- **The type governs a stylesheet** (the new *Its type* bullet). §7.1 said

SPEC.md §5.3, *A scrolling document*: the bullet on where a gesture goes
gains its last clause, and three bullets follow it:

```
  - A gesture scrolls the innermost element under the pointer that can
    still move that way. Where none can, it goes on outward, and past the
    root to the terminal, as if over the cells beneath (§9), unless CSS
    `overscroll-behavior` stops it there, or the host does (below).
  - **Past the edge on the alternate screen.** On the alternate screen,
    while the program has no mouse tracking mode on (DECSET 9 or 1000 to
    1003; an encoding such as 1006 alone is none), a gesture along
    an axis the document scrolls that goes past the root would reach the
    terminal only to become keys, or to do nothing, since that screen
    keeps no scrollback. The host **MUST** stop it at the root, as
    `overscroll-behavior: none` does, whatever the terminal's alternate

    scrolls it. Elsewhere it goes on as above: on the main screen to the
    scrollback, as a browser chains a scroll from a frame to its page, and
    to a program with mouse tracking on as its wheel. A gesture along an
    axis the document does not scroll is the terminal's, as over any
    other surface (§9).
  - **A multiplexer that relays the surface** (§2) does the same for the
    program behind it. Over the window of a surface whose document
    scrolls, the host passes on only gestures past its edge, and those
    along an axis it does not scroll. So the multiplexer drops a wheel
    there along an axis the document scrolls, where it would turn it into
    keys for that program (its alternate screen, with no mouse tracking
    on), and needs nothing but what it relays already: the placement and
    `scroll` (§5.1).
  - **A route kept for a gesture** holds per axis. A host that sends a
    gesture's events on where its first one went, as browsers latch a
    scroll to the element it first scrolls, keeps a route for each axis,

    with it.

```

    mouse tracking on, a wheel that reaches the terminal becomes arrow
    keys, on a terminal with alternate scroll, or nothing, since that

    swipe often opens with an event along the other axis, and a route

```

SPEC.md §9, a bullet after **A secondary press**:

```
- **Another button** is a mouse's button other than the primary and the
  secondary: the middle button, back and forward, and any other the
  platform reports. What the platform makes one of them is one, such as a
  touchpad's three-finger tap, which Linux makes the middle button. Its
  `button` is its number as the DOM gives it: 1 the middle button, 3 back,
  4 forward. A button the DOM has no number for is 6 or more, in the order
  the platform numbers its buttons (HOST.md). A host **MUST NOT** send
  `button` 5 in this version: Pointer Events give it to a pen's eraser.
  - **One subscription for every button.** An element takes them all with
    `aux` in its `data-on`, as `secondary` is one subscription for every
    gesture of a secondary press: the surface needs no `p`, and `p` alone
    never brings one. `aux` never takes the secondary button, which is a
    secondary press. The DOM's `auxclick` comes for every button but the
    primary; hotty's leaves the secondary out too.
  - **The press, then its release.** The press is reported as a `press`
    whose `t` is the nearest element with `aux`, from the pressed element
    outward, that is not a hyperlink (below), with its `button`, and `c`
    and `r`, the pointer's cell, as a secondary press has them. Until the
    button is released, the pointer is the surface's, as in a drag
    (§9.1), and its moves go nowhere. A release where that element is
    again the nearest with `aux` under the pointer reports `auxclick`,
    with the cell and the modifier keys held then: the press decides
    (§9.2), so a key pressed in between changes only `mods`. A release
    anywhere else reports nothing. What ends a drag early (§9.1) ends it,
    with no `auxclick`, and nothing says so.
  - **Without an id**, the element is reported with no `t` and no `area`,
    as for a secondary press. A link is the exception, as for a `click`:
    its `auxclick` carries its `href`, and its `area`.
  - **It does nothing else.** No `click`, no drag, no selection, no change
    of focus or of the keyboard (§10.1), and the terminal does nothing with
    it: no paste, no mouse report to the program.
  - **One button at a time.** While a press a surface took is held (a
    primary press or a drag, a secondary press, or another button's), a
    press of any other button is not reported and goes nowhere: not to
    the terminal, nor to the program's mouse reporting, until every
    button is released. Its release goes nowhere too. The other way round, while a press the terminal took is
    held (another button's over an element without `aux`, say), any other
    press is the terminal's too, over a surface as well, until every
    button is released, as a gesture with Alt is the program's to its end
    (§9.2).
  - **Only where asked.** Over an element without `aux`, inside or outside
    a surface, the press is the terminal's, as over the cells, and the
    surface hears nothing of it. The terminal does what it does with the
    press there: it pastes, say, or reports the press to a program that
    reads the mouse. A paste it makes of the press is its own paste
    (§11): while a text field has the keyboard, it goes into that field,
    and not to the program. A press on a hyperlink is the
    terminal's too, unless an element with `aux` holds it: a hyperlink
    belongs to the terminal (below), and its own `aux` counts for nothing.
    An `auxclick` never carries a hyperlink's `href`.
  - **A text field pastes.** Where the terminal's middle press pastes (the
    primary selection on Linux, or what the host's setting says, such as
    Ghostty's `middle-click-action`), a middle press on a text field
    (§10.2) is the field's, as in a browser. The field takes focus, and
    its caret goes to the pointer, as a click on it would put them
    (§10.1). What the terminal would paste goes in there, as its paste
    does (§11), with the field's own `input`, `caret` and `change`.
    Nothing else hears of the press. A field with `aux` in its
    own `data-on` takes the press as any element does, and the surface
    reports it. An `aux` on an element around the field does not take it.
    Elsewhere, and for back, forward and the later buttons, a field is like
    any other element.
  - **A host that cannot keep a button's own action** from its platform,
    such as a browser's history navigation for back and forward, does not
    report that button (HOST.md). It stays the platform's wherever it is
    pressed. A program offers another way to do what a button does, a key
    or a control, as it does for a secondary press.
  - **Buttons a program does not use.** A program **MUST** ignore a
    `press` or an `auxclick` whose `button` it does not use: later
    versions report more buttons.
  - **Shift and Alt** make it the terminal's or the program's (§9.2).
```

SPEC.md Appendix B, after **Why a secondary press**:

```
- **Why other buttons, by number.** A browser closes a tab on a middle
  click, and a mouse's back and forward buttons go back and forward
  through a history. A surface took only the primary and the secondary
  buttons, so a program could offer neither: a middle press over a
  surface was the terminal's.
  - **One word for every button,** not one for each. The secondary press
    has a word for its meaning, because several devices make it: a mouse,
    a pen, Control on macOS, a long touch. No other button is made by more
    than one. The middle button has no touch or pen form. What a platform
    makes one of, such as Linux's three-finger tap on a touchpad, is one as
    far as a program can tell. Back's and forward's other forms, a
    touchpad's swipes, are scrolls here (§9). A word for each button would
    also need a new version for each. So `aux` takes them all, `button`
    says which as the DOM numbers them, and a later button needs nothing
    new: a program ignores one it does not use.
  - **A press, then `auxclick`.** These buttons act on their release: a
    browser closes a tab when the middle button comes up over it, so a
    user who moves off first cancels. A menu opens on the press, which is
    why the secondary press has no release. The press still comes first,
    with a secondary press's detail, for a program that acts at once, and
    as the place a drag of another button would begin if one is ever
    added.
  - **`auxclick`, not `click`.** `click` is activation, which a key makes
    too, and every handler of it would have to check the button: the trap
    the DOM added `auxclick` to avoid. Its detail is a click's, with the
    button and the cell. Unlike the DOM's, it never comes for the
    secondary button, whose press does nothing else.
  - **One button at a time,** and no `buttons` field. hotty has no gesture
    of two buttons, and no move is reported while one is held. A button
    pressed by chance during a drag should neither end the drag nor reach
    the program. A field can be added if chords are ever wanted.
  - **The terminal keeps the rest.** A middle press nobody asked for
    pastes, as it always has over the cells (the primary selection on
    Linux), into the field with the keyboard if one has it (§11), and
    `p` brings only the primary button, so a surface that asks for presses
    takes nothing from the user. A text field pastes as a browser's does,
    and an `aux` around it leaves it that: a tab's rename field pastes, and
    does not close the tab.
  - **Shift for every button but the primary,** as for the secondary press:
    one rule, though Shift with back or forward does little in a terminal.
  - **A host reports only what it can take whole.** A browser cancels the
    back button's navigation only in some engines, and only on the
    release. A press the program heard while the page went back would be
    worse than none.
  - **Room for touch and pens:** `button` means the same on every device,
    as in Pointer Events. A touch makes 0, and its long press 2; a pen
    makes 0 and 2, and its eraser would be 5. A later field naming the
    device needs no change to it.
```

- **`data-keys-tree`** holds while the element is focused, or anything
  inside it is.

The focused element's keymap is, in order:
1. the default keymap, for a text field only (*Text fields*);
2. the `data-keys-tree` of each element from the document's root down to
   the focused element, its own included;
3. the focused element's own `data-keys`.

Each overrides what came before it key by key: a binding replaces the
earlier binding of its key, and leaves the others as they were. A program
sets its fields' keymap once, in the `data-keys-tree` of an element that
holds them. A field that needs one key otherwise says only that, in its
own `data-keys`.

Both attributes are a list of bindings separated by ASCII white space
(space, tab, line feed, form feed, carriage return), as HTML's
space-separated tokens are. A binding is `key=action`, split at its last
`=`: the key is read as §10.4 reads one (`ctrl+a`, `mod+s`,
`alt+arrow_left`; `alt+==line-start` binds `alt+=`), and the action is
one of the editing actions (*Text fields*), a scroll action (*Scrolling
keys*), `program`, `prefix`, or `default`. A host **MUST** ignore:
- a binding whose key does not parse or whose action it does not know;
- a binding to `default` in `data-keys-tree`;
- bindings of `shift+tab` and `escape`, and of `tab` to anything but
  `program` or `default`, which keep their meaning above.

**Each reader takes what it has a use for.** A keymap is read by the
focused element, by the surface with nothing focused, and by a selection
in the document (§11). A binding its reader does not take is as if it
were not there: it neither acts nor overrides the bindings before it.

| reader | takes |
| --- | --- |
| a text field | the editing actions, `program`, `prefix`, and `tab=program` |
| any other element | `program`, `prefix` and the scroll actions |
| the surface, with nothing focused | what any other element takes |
| a selection in the document | `copy`, with `program` and `prefix` as overrides of it (§11) |

- **`program`, `prefix` and `default` are overrides for every reader,**
  `default` from an element's own `data-keys` only (above). A nearer one
  replaces a farther binding of its key to any action, the selection's
  `copy` included: under `mod+c=program`, `ctrl+c` on Linux does not copy
  a selection (§11).
- **A key the focused element uses** it takes to `program` or `prefix`
  from its own `data-keys` only, never from a `data-keys-tree`. For a text
  field these are the keys it types: a character or `space`, with no
  modifier but `shift`. For any other element they are its row of the
  table at the start of §10.2: a button's `space` and `enter`, a select's
  characters and moves, a date input's keys. A list or a pager that gives
  `j` or `space` to the program in its `data-keys-tree` leaves its fields
  typing them, its buttons pressing on `space`, and its selects picking
  with `j`. A text field's editing keys are not among them: a tree's
  `arrow_down=program` reaches a field inside it, which takes the key
  back with `arrow_down=default` in its own `data-keys`.
- **With nothing focused,** the keymap is the `body`'s, as HTML makes the
  body the active element then: the `data-keys-tree` of the root and of
  the body, then the body's own `data-keys`, read as any other element's.
  A program writes them on its `body`: `<body
  data-keys-tree="mod+k=prefix">` in an `a=doc` payload, a whole document
  or a fragment, gives the body that attribute, as the HTML parsing
  algorithm does (§5.1). A payload with no `<body>` gives the body no
  keys of its own, and only the root's `data-keys-tree` holds; a second
  `<body>` in one adds only the attributes the body does not have yet. A delta's HTML never sets the body's attributes,
  since `<body>` is ignored where a fragment is parsed for an element: to
  change the body's keys later, a program gives the body an `id` and sets
  them with `attr` (§6.1), or sends a new document.
- **A selection's keymap** is the default keymap, then the
  `data-keys-tree` of the root and of the body, of which it takes
  `program` and `prefix` only, then the body's own `data-keys`. It takes
  `copy` from the body's own `data-keys` alone, and reads no other
  element's keymap (§11).
```

  focused where the root does not scroll; Appendix B says a field keeps
  its typed keys but not its editing keys; SDK.md's `element` reads the

- **Vectors:** the selection's `default` vector, which tested `cut`,

**Beyond the fixes**, for the maintainer to look at:
- **The root is the `body`.** The shape says "the root's own
  `data-keys`", and §5.1 never names the root. With nothing focused HTML
  makes the body the active element, and a payload, a fragment too, gives
  the body attributes with `<body …>`, so the draft names the body for
  both the keymap with nothing focused and a selection's. `data-keys-tree`
  still runs from the root (`html`) down, and `html`'s own `data-keys` is
  never read.
- **A selection reads the root's and the body's keys alone.** Today it
  reads the chain above the text it starts in, so a region could change
  its copy key. Nothing uses that.
- **0.8 sessions are read by alias,** if 0.9 speaks 0.8 at all: decide
  that with the release. If it does not, HOST.md §5.2 goes, and §5 says
  0.9 does not speak 0.8, as for a host that does not speak 0.7.
- **The SDKs' `Resolve` breaks** (`reader` for `multiline`, `own` apart
  from `tree`), and so does the keymap vectors' shape, in every SDK's
  runner. P-5 allows the break below 1.0, and in Go the `bool` no longer
  compiles.

**Considered and left out:** `default` in a `data-keys-tree`, giving keys
back for a region, such as a form inside a list giving the arrows back to
its fields. Nothing measured needed it once elements keep the keys they
use.

## Withdrawn

- **A modal region** (from hotty-surf, 2026-11-17; withdrawn the same day
  by the maintainer: no spec change). Plain HTML makes a dialog modal
  without any browser feature, and a hotty app can do the same. The
  program writes its own markup and hears every focus move. While a dialog
  is open it makes the page behind unfocusable (`tabindex=-1`, `disabled`),
  ignores that page's events, and focuses the dialog again on a `blur` or
  on a `focus` that lands outside it. hotty-surf's kit does this in the
  app.

- **A range input with keys and events** (from hotty-surf, 2026-11-17;
  withdrawn the same day by the maintainer). hotty defines no inputs: they
  come from HTML, and an app can hide one or build it in code.
  hotty-a2ui's range slider does that, with nothing added to the spec,
  using §9.1's `data-steps` drag.
