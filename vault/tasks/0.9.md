## To consider

- **A wheel past a scrollable surface's edge becomes arrow keys**
  (2026-11-16; the maintainer, scrolling the storybook's list fast with a
  trackpad: "I think it shouldn't be triggered in there", then "put it
  into 0.9 shelf").
  - **Today:** §5.3 sends a wheel the document can't take "past the
    root to the terminal", and §9 gives scroll gestures to the terminal
    except over a document that can still move that way. A full-screen
    program on the alternate screen without mouse mode then gets the
    terminal's alternate-scroll arrows: Ghostty's `scrollCallback` in
    hottyterm alone, plx's `mouseWheel` (d/alt-screen-wheel) in a plx
    pane, from the SGR wheel hottyterm forwards. Found by p-714
    (hotty-scroll-keys), code read.
  - **A second hole, same symptom without an edge:** hotty-blitz keeps a
    gesture's first route for 150 ms, and a terminal route matches any
    surface. A swipe that opens with an x-only event (mods/ghostty 0061)
    over a y-only document sends its vertical wheels to the terminal too.
  - **The shape talked through:** a document that scrolls along an axis
    keeps every wheel along it, so none becomes keys. The rubber band
    moved to 0.10 (2026-11-22), so this fix stands alone in 0.9. Its
    second hole, the 150 ms route, is closed for good only once hosts
    report a gesture's phases (0.10, *Rubber band*).
  - **Open for the spec:** a surface placed inline in a shell's normal
    screen chains a wheel at its edge to the terminal's scrollback today,
    like a browser's scroll chaining from an iframe to its page. Keep that
    and stop only what would become keys, or stop it too? The maintainer's
    call.

- **The focused element goes away: focus fixup, as in HTML** (2026-11-17;
  hotty-surf p-653, from its L2 display review: a closing toast's button,
  and Basecoat's toast.js blurring by hand).
  - **Today:** §10.1 never says what happens when the focused element
    leaves the document, or stops taking focus (disabled, hidden, not
    rendered, inert). Neither does HOST.md. Hosts may differ. The cells
    renderer already drops focus with no `blur` (hotty-surf L1: "a
    disabled or hidden field loses the keyboard … with no blur").
  - **Nothing in the spec gives "nothing focused" on request:** `a=focus`
    without `t` keeps the focused element or focuses the first one.
    `a=blur` gives the keyboard back to the terminal. A page's
    `activeElement.blur()` keeps the keyboard in the page with nothing
    focused; hotty has no counterpart.
  - **The reviewer's proposed wording (§10.1):** "When the focused element
    leaves the document, or stops taking focus (disabled, hidden, not
    rendered, inert), it loses focus. The surface keeps the keyboard with
    nothing focused, and the host sends no `blur`. Keys then reach the
    program (§10.2, *Keys for the program*)."
  - **With it, the kit needs no blur API:** a closing toast's buttons
    are written `disabled` from the frame it closes in, and a popover's
    `invisible` drops focus as a browser's does. hotty-surf makes
    `Autofocus(ctx, "")` a fault meanwhile, and adds `surf.Blur` (meaning
    `a=blur`) only if a component ever has to hand the keyboard to the
    terminal.
  - **Leans taken** (2026-11-17, under the maintainer's rule that day,
    "nothing waiting for my approval, take the leans", relayed by gov
    p-753). The reviewer's wording goes into §10.1 when 0.9 is drafted,
    with these answers:
    - **The program is told nothing,** as HTML's focus fixup fires no
      event. A program that removes or disables the element knows it did.
      For one hidden by layout alone, the next key goes to the program
      (§10.2), which shows it nothing is focused.
    - **When the check runs:** each time the host lays the document out,
      after the program's changes and after a resize, as a browser
      runs focus fixup when it updates the rendering.
    - **`opacity: 0` doesn't count,** nor does anything else that leaves
      the element rendered and focusable in a browser. `visibility:
      hidden`, `display: none`, `disabled`, `inert` and leaving the
      document do count.
  - **Drafted** (2026-11-22, on `hotty-0.9`): SPEC §10.1, §16 and
    Appendix B, SDK.md §4.4, the vectors and their README. For the
    maintainer to sign: [the wording](#focus-fixup-the-wording), with
    its [legs](#focus-fixup-legs).

- **A pointer's other buttons: one shape for all of them** (2026-11-19;
  from plx p-815: a middle press on a workspace tab should close it, and a
  surface drops it today).
  - **The maintainer:** file it for 0.10 (folded into 0.9 on 2026-11-22), but first "see if it makes sense
    to keep adding buttons one by one". The secondary press (V7-01, 0.7)
    was named for its meaning, not as button 2, so a touch's long press, a
    pen's barrel button and macOS's Control-click are one gesture. A mouse
    also has buttons 4 and 5, back and forward (DOM `button` 3 and 4), which we might want to
    track. Find a shape that doesn't need a new subscription for each
    button.
  - **Today (§9):**
    - `press` reports the primary button wherever `p` is on.
    - A secondary press needs `secondary` in `data-on`, and arrives as
      `press` with `button: 2` and `c`/`r`. `button` uses DOM numbering
      (`MouseEvent.button`).
    - Nothing else is reported. A middle, back or forward press over a
      surface is the terminal's, as over the cells. So in a terminal, plx
      loses middle-click-to-close on its tabs, which it still has in the
      cells.
  - **Questions for the shape:**
    - **Meaning or button?** Is each new subscription a meaning, as
      `secondary` is (`middle` → "auxiliary"? `back`/`forward` → history
      navigation?), or a button number? Is one opt-in enough for "any
      other button", with `button` saying which? A meaning maps to touch
      and pen. A number doesn't. Middle has no touch counterpart. Back and
      forward have trackpad swipes as their platform gestures, which hosts
      already use for scrolling.
    - **`button` vs `buttons`:** is a press's `button` the only field, or
      do chords (two held at once) matter? Browsers report both.
    - **Releases and drags:** does another button's press start a drag
      (§9.1) or a click (`auxclick` in the DOM), or is it a press alone,
      like the secondary press ("it does nothing else")?
    - **What the terminal keeps:** a middle press pastes the primary
      selection on Linux. Over an element that asks for it, the surface
      takes it; elsewhere it stays the terminal's. Shift/Alt (§9.2) as for
      the secondary press?
    - **Hosts:** what each one can see. Ghostty's mouse buttons reach 11.
      xterm.js reports middle. Blitz gets winit's `Back`/`Forward`/`Other`.
    - **SDKs:** hotty-surf's handler shape (one `surf.Press` with a button,
      or a handler per meaning), as `surf.Secondary` is today.
  - **Wanted from the draft:** one shape that covers middle now, and back,
    forward and later buttons without another spec change.
  - The maintainer's call.

- **An identical resource resend may change nothing** (2026-11-19; from
  hotty-blitz 0.8.11).
  - **The case:** plx sends its kit stylesheet again on every tab switch.
    hotty-blitz now ignores an `a=res` whose id, type and bytes match the
    stored resource, so the 12 surfaces linking it are not restyled. A
    switch drops from ~57 to ~24 ms.
  - **Today (§7.1):** "sending a resource again replaces it, and every
    surface that refers to it is drawn again". Drawing the same bytes
    again draws the same pixels, so a program can't see the difference.
  - **The maintainer (2026-11-19):** an identical resend must not restart
    an animated image. hotty-blitz never restarted one anyway, because it
    didn't reload a re-sent `cid:` image at all.
  - **For the maintainer:** should §7.1 say a host MAY ignore a
    byte-identical resend and MUST NOT restart an animation for one? Or
    leave the text as it is?

- **A surface's `program` key that is a command the program took**
  (2026-11-21; from hotty-surf's blind review of its edit-shortcut
  keymaps; the maintainer took it for 0.9 on 2026-11-22).
  - **The case:** a program in the cells takes the edit commands
    (`a=edit:take=copy,…`, §10.6). Its surface's keymap binds a key that is
    one of the host's edit shortcuts to `program` (§10.2), such as
    `ctrl+c=program` on Linux. Does the key reach the program as its bytes
    (`ctrl+c`), or as the event `command` (`copy`, with `key: ctrl+c`)?
  - **Today:** §10.6 says "a key it does not use reaches the program as
    the command", and §10.2 says a key bound to `program` reaches it "as
    terminal input". Neither says whether a `program` binding counts as
    the surface using the key, so hosts may differ. Nothing hits it yet:
    hotty-surf takes no `a=edit`.
  - **Lean: as the command.** A `program` binding means the surface
    doesn't use the key, so §10.6's rule applies. The command carries the
    key, and a program with nothing selected takes it as its key anyway.
    §10.2 or §10.6 would say so in one sentence.
  - The maintainer's call.

- **`data-keys` is the element's own; `data-keys-tree` inherits**
  (2026-11-22; the maintainer, from hotty-surf's edit-shortcut keymaps,
  where an edit group can't go on a container and is written on every
  field instead).
  - **Today (§10.2, §10.5, §11):** every `data-keys` reaches every focused
    element inside it, of every kind, and a document selection's copy reads
    the same chain. So a binding leaks where it doesn't belong:
    - `ctrl+c=copy` on a container also copies a document selection on
      a Mac, where Ctrl+C should interrupt;
    - a list's `space=program` reaches its buttons and fields, each of
      which then needs `space=default`;
    - the edit shortcuts go on each field, about 200 B a field (20 KB on
      a table of 100 editable cells).

    A field also leaves scroll actions out under a rule of its own.
  - **Inheritance is still needed for some cases:**
    - a leader or prefix (`mod+k` anywhere in a view);
    - a list whose rows take focus, with its arrows on the list;
    - a pager's `j` and `k` while a link inside it is focused;
    - a pane's shortcuts from any field or button in it.

    So it becomes opt-in, not dropped.
  - **The shape:**
    - **`data-keys`** is the element's own. It applies only while that
      element has focus.
    - **`data-keys-tree`** applies while focus is on the element or
      anything inside it. Its syntax is the same as `data-keys`. It is an
      attribute of its own, not a marker inside `data-keys`, because key
      names already use `+`, and because one value then carries one scope
      and a delta changes one scope.
    - **A focused element's keymap** is built in three steps. It starts
      from the default keymap, for a text field only. Then comes
      `data-keys-tree` from the root down to the element, its own
      included, with the nearer element winning key by key, as today.
      Last comes the element's own `data-keys`, which wins. In its own
      `data-keys`, `key=default` cuts off an inherited binding, and that
      is `default`'s only use.
    - **The document's keymap** is the root's own `data-keys`. It applies
      with nothing focused, and §11's selection copy reads it. Tree
      bindings never apply to a selection.
    - **One rule for every reader:** a reader ignores a binding whose
      action it does not take, as if it were not there, so the binding
      neither acts nor overrides. This replaces two rules: a field leaving
      scroll actions out, and other elements letting editing actions
      override and then do nothing.
  - **What it gives:**
    - The edit shortcuts go on the root once, as tree. Fields take them,
      buttons ignore them, and a selection doesn't see them, so the Mac's
      Ctrl+C still interrupts.
    - A list's keys are its own, so its buttons keep Space without a
      give-back.
    - A pager's tree `j` scrolls from a link and types in a field.
  - **No per-context attributes** (field, focus, selection). Weighed and
    not needed with the above.
  - **The gap left:** a tree binding to `program` or `prefix` of a key a
    field also uses still reaches the field, such as a scope forwarding
    `j` with a search field inside it. The field cuts it with its own
    `j=default`, and hotty-surf can write that cut itself. If a blind
    review or plx's measurement finds many such cuts, add a field-only
    tree attribute then.
  - **Compatibility:** none (the maintainer). Documents that rely on
    inheritance through `data-keys` change meaning, and programs and
    hosts negotiate 0.9 under §15.
  - **What changes outside the spec:**
    - every host's root-down walk: hotty-blitz, xterm-addon-hotty, and
      hotty-surf's cells;
    - `hotty.Resolve` in hotty-go, and its counterparts in hotty-ts,
      hotty-rs and hotty-lua;
    - hotty-surf's writer, where `KeyScope`, prefixes and groups bound
      on a root become tree, and the rest own;
    - hotty-a2ui (paused) and the web/hotty demos.

    plx writes no `data-keys` of its own, so it only follows hotty-surf.
  - Before drafting: a blind review of the shape. Then measure plx's
    longest list under its KeyScope and leader, in bytes and deltas,
    before and after.

### Focus fixup: the wording

SPEC.md §10.1, a bullet after **A click elsewhere gives the keyboard
back**:

```
- **The focused element goes away.** When the focused element leaves the
  document, or stops taking focus, it loses focus, as HTML's focus fixup
  has it. The surface keeps the keyboard with nothing focused (§10.2).
  - **What counts:** the element removed, by a delta or a new document
    (§5.1, §6); made `disabled` or `inert`, or put inside an `inert`
    element; or no longer rendered, by `display: none`, `visibility:
    hidden`, a closed `details` or a `hidden` attribute, its own or an
    ancestor's. `opacity: 0` does not count, nor does anything else that
    leaves the element rendered and focusable in a browser: scrolled out
    of view, clipped, covered, or outside the placement's window (§5.2).
  - **When the host checks:** each time it lays the document out, after
    the program's changes and after a resize, as a browser runs focus
    fixup when it updates the rendering.
  - **The program is told nothing,** as HTML's focus fixup fires no
    event: no `blur`, no `focus`, and no `change`. A program that removed
    or disabled the element knows it did. For one that layout alone hid,
    the next key reaches the program (§10.2), which shows it nothing is
    focused. A value the user changed and did not commit stays in the
    field, and a `submit` of its form still carries it.
  - **With nothing focused,** every key but a scrolling document's own
    scrolling keys (§5.3) reaches the program, with no keymap (§10.2,
    *Keys for the program*). `tab` focuses the first focusable element,
    as `a=focus` without `t` does, and `shift+tab` the last; with none,
    the surface loses the keyboard, as past the last (§10.2). A prefix
    (§10.5) goes on, since the surface kept the keyboard.
```

SPEC.md Appendix B, a bullet before **Why scrolling keys**:

```
- **Why focus fixup sends nothing.** A component that closes, such as a
  toast whose button had focus, disables or hides what it shows, and the
  host has to do something with the focus it held. HTML's answer is focus
  fixup: the document keeps the keyboard with nothing focused, and no
  event fires. A `blur` would say the terminal has the keyboard, which it
  does not, and a `focus` on some other element would move the user where
  neither they nor the program went.
  - **The program knows already** where it removed or disabled the
    element, and where layout alone hid it, the next key reaches it,
    which is what nothing focused means to it.
  - **No blur of its own.** With fixup, a program that wants nothing
    focused disables or hides the element, as a page does, so hotty needs
    no counterpart of a page's `activeElement.blur()`. `a=blur` still
    gives the keyboard to the terminal.
  - **On layout,** because `display: none` and `visibility: hidden` come
    from styles, a media query or a resize as much as from the program's
    deltas, and only layout knows what is rendered.
```

SPEC.md §16: the vectors check "focus fixup".

SDK.md §4.4, the test host: it keeps the focused element and drops focus
with no event where a delta or a document removes it, makes it
`disabled` (by a `disabled` fieldset too), or makes it or an ancestor
`inert` or `hidden`. What CSS hides it cannot see, so it skips the vectors
marked `layout`, a new name in conformance/README.md.

Two vectors, after "there is one keyboard":
- removed, `disabled`, inside a `disabled` fieldset, and `inert`: no
  event, keys reach the program, then `tab` and `a=focus` without `t`
  focus the first focusable element, and `shift+tab` with none left sends
  `blur`;
- `layout`: `display: none` from a class, `visibility: hidden`, a
  `details` closed, and a media query a resize turns on drop focus, and
  `opacity: 0` does not.

**Beyond the leans**, for the maintainer to look at:
- **No `change` either.** A field the user edited and that fixup takes
  focus from commits nothing then. Its value stays, and its form's
  `submit` carries it. Focus leaving a field commits it today (§9), so
  this is a choice: no event at all, as the lean says, over a commit.
- **Tab from nothing focused** goes to the first focusable element, and
  Shift+Tab to the last. A browser goes on from where the element was (its
  focus navigation starting point), but hosts would then have to remember
  a removed element's place. The first and the last are what `a=focus`
  without `t` already does.

### Focus fixup: legs

- [x] hotty: the wording above, the vectors and the README's `layout`.
- [ ] hotty-blitz: after each layout (a delta, a `doc`, a placement that
  resizes, a resource that restyles), drop focus from an element that is
  no longer connected, focusable, rendered or visible, with no event and
  no commit; Tab and Shift+Tab from nothing focused. Check that Blitz
  honours `inert` and a closed `details`; a mods/blitz patch with its `.md`
  if not. Its runner adds `layout` to what it runs.
- [ ] xterm-addon-hotty: the browser runs the fixup itself, but Chromium
  fires `blur` and `focusout` on the element it removes or hides, which
  the addon must not report as `blur` or commit as `change`: tell a fixup
  (the old element disconnected or no longer focusable, and no new one)
  from a move. Tab from nothing focused as above, where the browser's
  starting point would differ. Its e2e runner adds `layout` to
  `reported`.
- [ ] hotty-go (hottytest), hotty-ts, hotty-rs, hotty-lua: the test host's
  fixup as SDK.md §4.4 says, and their runners skip `layout`. No wire
  change, so no builder, decoder or SDK vector.
- [ ] hotty-surf: the cells renderer already drops focus with no `blur`;
  give it Tab and Shift+Tab from nothing focused. The kit writes a closing
  toast's buttons `disabled` from the frame it closes in, and keeps
  `Autofocus(ctx, "")` a fault; no `surf.Blur` until a component has to
  hand the keyboard to the terminal.
- [ ] hottyterm: the re-pin of hotty-blitz, with wave 3.

## Withdrawn

- **A modal region** (hotty-surf p-653, 2026-11-17; withdrawn the same day
  by the maintainer: no spec change). Plain HTML makes a dialog modal
  without any browser feature, and a hotty app can do the same. The
  program writes its own markup and hears every focus move. While a dialog
  is open it makes the page behind unfocusable (`tabindex=-1`, `disabled`),
  ignores that page's events, and focuses the dialog again on a `blur` or
  on a `focus` that lands outside it. hotty-surf's kit does this in the
  app.

- **A range input with keys and events** (hotty-surf p-653, 2026-11-17;
  withdrawn the same day by the maintainer). hotty defines no inputs: they
  come from HTML, and an app can hide one or build it in code.
  hotty-a2ui's range slider does that, with nothing added to the spec,
  using §9.1's `data-steps` drag.
