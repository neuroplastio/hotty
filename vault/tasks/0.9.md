# hotty 0.9

Items for the version after 0.8. Nothing here is accepted or built yet.

Item template: as `tasks/0.4.md`.

## To consider

Notes, not proposals: each is to be weighed for 0.9 before anyone drafts it.

- **Rubber band and momentum on a scrolling document** (2026-11-16; the
  maintainer asked for "the rubber / spring effect when overscrolling with
  trackpads / touchscreens, similar to the browsers. Only for
  hotty-scrollable surfaces", then: "Let's shelve it for 0.9").
  - **Today:**
    - hottyterm hands a trackpad's scroll and a touch drag to a document
      that scrolls (§5.3) as precision pixel deltas (mods/ghostty 0009,
      0014).
    - A touch drag's end reaches hotty-blitz (`hotty_host_end_gesture`). A
      trackpad swipe's end and its lift velocity (GTK's scroll-end and
      `decelerate`) probably don't. Check first.
    - hotty-blitz clamps a scroll at the edge (`scroll::scroll_by`), so
      nothing stretches, and a flick has no momentum after the lift.
  - **The shape talked through (host behaviour, as scrollbars and snapping
    are):**
    - hottyterm passes the gesture's phases and its lift velocity (AppKit
      has both).
    - hotty-blitz rubber-bands past an edge during a precision gesture,
      with resistance growing with the distance, as Safari does, and
      springs back on release with a damped spring.
    - A fling coasts with friction and bounces at the edge.
    - Scroll acceleration (2026-11-16, the maintainer: "I want scroll
      acceleration when using touchscreen or trackpad (for 0.9)"): a run
      of quick swipes in one direction goes further each time, as on macOS
      and in browsers. It is the same host-side gesture model as the fling.
    - A notched wheel gets neither.
    - `overscroll-behavior: none` turns the bounce off for its box, and
      `contain` stops the chaining, as browsers do.
    - Reduced motion (V8-02) turns it off.
    - Paint only, on the frame timer that already fades scrollbars and
      settles snaps. Never a relayout.
    - xterm-addon-hotty would need its own, since the iframe can't use
      the browser's bounce for a document it scrolls itself.
  - **Open for the spec:** is a program told about overscroll? The lean is
    no: browsers fire no scroll events for the bounce. §5.3 would say so,
    so hosts agree. That is the maintainer's call.

- **A wheel past a scrollable surface's edge becomes arrow keys**
  (2026-11-16; the maintainer, scrolling the storybook's list fast with a
  trackpad: "I think it shouldn't be triggered in there", then "put it
  into 0.9 shelf").
  - **Today:** §5.3 sends a wheel the document can't take "past the
    root to the terminal", and §9 gives scroll gestures to the terminal
    except over a document that can still move that way. A full-screen
    program on the alternate screen without mouse mode then gets the
    terminal's alternate-scroll arrows: Ghostty's `scrollCallback` in
    hottyterm alone, plx's `mouseWheel` (d/alt-screen-wheel) in a plx
    pane, from the SGR wheel hottyterm forwards. Found by p-714
    (hotty-scroll-keys), code read.
  - **A second hole, same symptom without an edge:** hotty-blitz keeps a
    gesture's first route for 150 ms, and a terminal route matches any
    surface. A swipe that opens with an x-only event (mods/ghostty 0061)
    over a y-only document sends its vertical wheels to the terminal too.
  - **The shape talked through:** a document that scrolls along an axis
    keeps every wheel along it, so none becomes keys. It belongs with the
    overscroll item above (the rubber band needs the wheel past the edge
    anyway).
  - **Open for the spec:** a surface placed inline in a shell's normal
    screen chains a wheel at its edge to the terminal's scrollback today,
    like a browser's scroll chaining from an iframe to its page. Keep that
    and stop only what would become keys, or stop it too? The maintainer's
    call.

- **A modal region: a dialog that keeps the keyboard and makes the rest
  inert** (2026-11-17; hotty-surf p-653, from ui.Dialog and Toaster in
  hotty-surf L1 on branch v07, "a protocol gap with no workaround in the
  kit". The repro is p-653's).
  - **Today, a dialog in a document can't be modal:**
    - Tab, Shift+Tab and other focus moves leave the dialog for the page
      behind it.
    - Clicks, hover and keys still reach the elements behind it.
    - A click on the dialog's own text, not a control, blurs the field
      inside it, so the keyboard leaves the dialog: §10.1 gives the
      keyboard back to the terminal, with `blur`, on a click inside a
      surface on an element that takes no focus.
  - **Browsers** do this with `<dialog>` shown by `showModal()`, and with
    `inert` on the rest of the page. hotty documents have no script to
    call `showModal()`.
  - **The shape asked for:** a program marks a modal region in its
    document, either by honouring `inert` on the rest or with a dialog
    element shown modal (such as `<dialog open data-modal>`; the name is
    open). The host then keeps focus inside the region, makes the rest
    inert (no clicks, hover or focus), and treats a click on text inside
    the region as staying in the surface.
  - **Open for the spec:** `inert` alone (the HTML attribute, no new
    name) or a declared modal dialog; whether a click outside the region
    is sent to the program (a backdrop click usually closes a dialog);
    what Escape does, and whether the host or the program closes it; and
    whether §10.1's click rule changes for every surface or only inside a
    modal region. The maintainer's call.

- **A range input with keys and events** (2026-11-17; hotty-surf p-653,
  from its L2 forms review. hotty-surf cut `ui.Range` until the spec
  covers one).
  - **Today:**
    - §6.4's `a=field` already clamps and steps a range's `value`.
    - A slider can be built from §9.1's `data-steps` drag. A native
      `input type=range` gets no keys in §10.2 and no event in §9.
    - hotty-blitz draws no range input (its gap list has it).
  - **The reviewer's proposed wording:**
    - **§10.2, keys:** a focused `input` of type `range` uses
      `arrow_left` and `arrow_down` (a step down), `arrow_right` and
      `arrow_up` (a step up), `home` and `end` (its min and max), and
      `page_up` and `page_down` (a larger step, as the host likes),
      unmodified or with `shift` only.
    - **§9, events:** a range moved by a key or the pointer is heard at
      once, as a select's pick is: `input` with `data-on~=input`, then
      `change`, `{"value": str, "rev": int}`. A press on its track, or a
      drag along it, moves it.
    - **Hosts:** hotty-blitz draws the track and the thumb. The cells draw
      a bar, for example `[====·····]`.
  - **Open for the spec:**
    - **When `change` fires during a drag:** browsers send `input` on
      each move and `change` once, on release. The proposal hears both
      at once, as a select's pick is heard.
    - **Vertical and right-to-left ranges:** which way an arrow steps.
    - **How a drag on a range relates to §9.1's `data-steps` drag.**
  - The wording is the maintainer's call.
