# hotty 0.7: `scroll`, Tab in a field, a key given back

What breaks 0.6. At the 0.6 cut the maintainer moved three accepted items
here from `tasks/0.6.md` (2026-11-01: "scroll op, Tab-in-a-field and
key-back move to 0.7"), and two proposals came with them, out of the cut.
They keep their V6 ids, their text and their acceptance. Their text was
written while 0.6 was to come: where it names 0.6 as the next version (a
branch, the version a program meets a host at), read 0.7, and read its
wording against 0.6's SPEC.md. Since 0.6 a scroll comes to rest on a snap
position (V6-04, SPEC §5.3), so V6-01's op, which moves as a key's step
does, comes to rest as one does.

Each item lands in SPEC.md, SDK.md and the vectors together (AGENTS.md),
on local branches across the stack, as 0.5 and 0.6 did.

Item template: as `tasks/0.4.md`.

## Accepted

- [ ] **V6-01** `scroll`: a program scrolls a surface by the steps of the scrolling keys
      status: accepted, drafted, held; accepted by the maintainer, 2026-10-25 ("`scroll` op with actions"); moved to 0.7 at the 0.6 cut (the maintainer, 2026-11-01) | added: 2026-10-25
      problem: scrolling is local (§5.3). A program moves a surface only
      by focus or `reveal`, and its keys scroll it only as `data-keys`
      bindings to scroll actions (§10.2), which the host applies while the
      surface has the keyboard. A program that keeps the keyboard in the
      terminal, with a keymap of its own (modes, counts, the user's
      configuration), cannot hand its keys to the host as data, and some
      of them scroll only on a condition the host cannot know. margin, a
      reader, would move its document column to one scrolling surface, and
      needs:
      - `j` and `k` through a block taller than the window, moving focus
        to the next block only once the block's end shows. Prose has no
        element per line for `reveal` to bring into view.
      - Its own paging keys (Space, `page_down`, `ctrl+d`, `ctrl+u`), with
        counts.
      - `h` and `l` on a code block or a table that scrolls across.
      proposal: a delta op, `scroll`, whose `v` is one of §10.2's scroll
      actions. It scrolls as a key bound to that action would with focus
      on the target: the nearest element that scrolls, from the target
      outward, itself included, then outward as a gesture goes, never past
      the root. An empty `t` starts at the root.
      - Each op moves one of the host's steps, the step its key takes,
        not an amount: rows of the terminal do not map onto prose the host
        wraps, and pixels are not the program's unit. A count is as many
        ops, and n ops move n steps even while a smooth scroll still
        moves.
      - It moves as the key does on that host, smooth or not. It stops a
        gesture's momentum, and a gesture takes over from it.
      - Where nothing can move, or along an axis the document does not
        scroll, it does nothing and is no error. The program hears where
        things came to rest from `view` (§9.5), as after any scroll.
      - It works whether the surface has the keyboard or not, moves
        neither focus nor the keyboard, and sends no event of its own.
      - A `v` that is not a scroll action is `EINVAL`.
      cost: one op for every host. Both already find the box and take the
      step for scrolling keys (hotty-blitz `scroll.rs`, the addon's
      `scrollBox`), so the op calls that code from a delta. Each SDK adds
      `ScrollOp` and `Scroll`, and the test hosts move offsets as they do
      for `reveal`. A 0.5 program meets a 0.6 host at `EVERSION`, as at
      every minor.
      legs (local `hotty-0.6` branches, pushed when all have landed):
      - [x] hotty: the wording below, in the vault (2026-10-25)
      - [ ] hotty: SPEC §5.3, §6.1, §10.2, §16, App. B; SDK.md; vectors;
        Python client; CHANGES; docs
      - [ ] hotty-go (+ hottytest), hotty-ts, hotty-lua, hotty-rs
      - [ ] hotty-blitz, xterm-addon-hotty, hottyterm re-pin
      - [ ] plx relay, margin, web/hotty and the docs site's pins, which
        follow the release
      settle while building: a multiplexer that keeps deltas for the
      terminal that attaches (§3.6 `ENOTERM`) would replay a scroll the
      user never saw; `reveal` already has the same question. margin's
      lean (2026-10-25): replay neither, so a late terminal starts at the
      top; margin brings its focused block into view again after that
      terminal's first `view`.

### V6-01: the wording

**§5.3**, the bullet *Scrolling is local*:

> - Scrolling is local: the program hears of it only where it asks, which
>   elements are in view (§9.5), and moves it only by focus (§10.1), by
>   bringing an element into view (`reveal`, §6.1), or by the steps a
>   scrolling key takes (`scroll`, §6.1). A delta keeps the offsets
>   (§6.2), and a new document starts at the top left.

**§6.1**, a row after `reveal`:

> | `scroll` | a scroll action (§10.2) | scroll as a key bound to the action would, from the target (below) |

**§6.1**, *Checked first*: `t` is missing or empty where the op needs one
"(every op but `morph`, for which an empty `t` is none, and `scroll`, for
which it is the root)", and the last case reads "or `reveal` has a `v`
other than `start` or `end`, or `scroll` one that is not a scroll action
(§10.2)".

**§6.1**, a bullet after *Reveal*:

> - **Scroll** changes no node. It scrolls as a key bound to its `v` would
>   with focus on the target (§10.2, *Scrolling keys*), whether the surface
>   has the keyboard or not: the nearest element that scrolls, from the
>   target outward, itself included, or the root when `t` is empty. Where
>   that cannot move that way, it goes outward as a gesture does (§5.3), as
>   far as `overscroll-behavior` lets it, and never past the root.
>   - **One step** of the host's for each op, the one the action's key
>     takes, so a program scrolls by a count with as many ops. A host that
>     animates the key animates the op, and each op starts from where the
>     one before it was going, not from where the box is drawn, so n ops
>     move n steps. An op stops the momentum of a gesture, and a gesture
>     takes over from an op still moving.
>   - **Nothing to move** is no error. Where nothing it may reach can move,
>     along an axis the document does not scroll (§5.1 `scroll`), and in a
>     surface not placed, it does nothing.
>   - Like `reveal`, it moves neither focus nor the keyboard (§10), and
>     sends no event of its own: elements that report whether they are in
>     view report it once the scroll comes to rest (§9.5).

**§10.2**, *Scrolling keys*, after the example of `data-keys`:

> A program that keeps the keyboard, or scrolls only on a condition of its
> own, scrolls by the same steps with the `scroll` op (§6.1).

**§16**: the vectors check "`reveal`, `scroll` and `view`".

**Appendix B**, after *Why `reveal` and `view`*:

> - **Why a `scroll` op.** Scrolling keys (§10.2) serve a program that can
>   hand its keys to the host as data. One that keeps the keyboard in the
>   terminal, with a keymap of its own, its modes, counts and the user's
>   configuration, cannot, and some of its keys scroll only on a condition
>   of its own: `j` in a reader scrolls through a block taller than the
>   window, and moves to the next block once the block's end shows. Prose
>   has no element per line for `reveal` to bring into view.
>   - **The host's steps, not an amount.** The host wraps the prose, so
>     rows of the terminal do not map onto its lines, and pixels are not
>     the program's unit. The steps are those the user's own keys take,
>     so the program's keys and the surface's agree.
>   - **From a target, as a key from focus,** so one rule says what
>     scrolls: a code block that scrolls across takes `h` and `l`, and the
>     document around it `j` and `k`.
>   - **Still local.** Gestures stay the host's, the program hears where a
>     scroll came to rest only from `view`, and an op that can move
>     nothing does nothing, as a key does.

**SDK.md**:
- *delta ops* gains `scroll`.
- The op builders gain `ScrollOp`: op `scroll`, parameters target
  (empty: the root) and action.
- The messages gain `Scroll`: `Delta` with one op, `ScrollOp`, where
  action is a scroll action (SPEC.md §6.1); parameters surface, target,
  action; level 2.
- The key order: `t` unless the target is empty, and `v` always.
- The names table: `hotty.OpScroll` and `Scroll` in Go, `scroll_op` and
  `scroll` in Python, `scrollOp` and `scroll` in TypeScript.

**Vectors**: build `ScrollOp` and `Scroll`, with a target and without.
Hosts:
- `EINVAL` for a `v` that is none, `start` or `down`;
- `ENOTARGET` with the id as detail;
- a surface not placed answers ok;
- in a long document, `scroll-end` then `view` with `end: true`, and
  `scroll-start` back;
- `scroll-down` from an element that cannot move reaches the root;
- along x in a document of `scroll=y`, nothing.

A host chooses its steps, so the vectors check which box moved and what
`view` reports, not by how much, except at the ends.

- [ ] **V6-02** A text field may give the program `tab`
      status: accepted; accepted by the maintainer, 2026-10-30 ("prefer
      browser-like model where default behavior is standard, but the app
      can still override it"); moved to 0.7 at the 0.6 cut (the maintainer, 2026-11-01) | added: 2026-10-29
      problem: a command palette or a picker completes what was typed on
      Tab, as shells and fuzzy finders do, and its users expect it. In
      the cells it can. On a surface it cannot: Tab moves focus, and a
      host ignores a `data-keys` binding of `tab` (§10.2), so the program
      never hears it from its field. A palette whose field is its only
      focusable element hands the keyboard back to the terminal on Tab
      instead. The program has to pick another key, one users of its
      cells version don't know.
      proposal: a host honours `tab=program` in a text field's keymap
      (§10.2), and only there. `shift+tab` and `escape` keep their
      meaning everywhere, and `tab` keeps it on every other element.
      - The field gives the program `tab`, which reaches it as any key a
        field gives does. The program decides: it completes with
        `a=field` (§6.4), or moves focus itself with `a=focus`.
      - Shift+Tab still moves focus back, and Escape still reaches the
        program, so a user always has a way out of the field.
      - Only a text field: a button or a list has no reason to keep Tab,
        and focus order stays the host's.
      cost:
      - §10.2: "bindings of `tab`, `shift+tab` and `escape`" becomes
        "bindings of `shift+tab` and `escape`, and of `tab` to anything
        but `program` or outside a text field".
      - SDK.md: Keymap and Resolve read the binding.
      - Vectors: a field with `tab=program` gives the program `tab`; one
        without moves focus.
      - Forward Tab past such a field takes Shift+Tab or a key the
        program binds: an accessibility cost a program takes on by
        binding it.
      - Not breaking: a binding hosts ignore today starts to hold.

- [ ] **V6-05** A keymap may give a key back to the host
      status: accepted; accepted by the maintainer, 2026-10-30; moved to 0.7 at the 0.6 cut (the maintainer, 2026-11-01) | added: 2026-10-30
      problem: §10.2 merges `data-keys` from the root down. A key an
      element gives the program holds for everything inside it, and no
      action takes it back.
      - A list that binds Space to the program, to toggle its rows, takes
        Space from a button inside it, which Space should press, and
        from a text field inside it, which should type a space. A
        framework that writes such a keymap has to put stand-ins on the
        button (`space=scroll-page-down`, so Space at least scrolls) and
        has no stand-in at all for typing.
      - The same holds for every key a field types and an ancestor binds:
        a letter that a list uses as a shortcut can't be typed in a field
        inside it.
      proposal: an action `default`. `key=default` in an element's keymap
      gives that key back to the host's own meaning for that element and
      what is inside it, as if no element above had bound it: Space
      presses a button and types in a field, an arrow scrolls or moves a
      caret. It is an override like any other, and the nearest binding
      still wins.
      - Browser-like: the default action is the browser's, and a page
        gives it back by not calling `preventDefault` in the inner
        element's handler. `default` is that, as data.
      cost:
      - §10.2: the action, beside `program` and the scroll actions.
      - SDK.md: Keymap and Resolve read it.
      - Hosts: the keymap's resolution stops at a `default` and does what
        it would with no keymap.
      - Vectors: a button inside a list that binds Space, with and
        without `space=default`; a field likewise, with a letter.
      - Not breaking: no keymap has the action today.

## Proposed

- [ ] **V6-08** A column is a cell: the terminal's font in a surface keeps to the grid
      status: proposed, a draft; accepting it is the maintainer's | added: 2026-10-31
      out of the 0.6 cut (the maintainer, 2026-11-01), and proposed for 0.7
      problem: §8 makes a row one cell (`line-height:
      var(--hotty-cell-h)`, so 1rlh is a row) and says nothing of
      columns. A terminal rounds its cell from the font's advance; a
      surface's text in `--hotty-font` keeps the advance. hottyterm at
      1.6, measured on one machine's font and size, draws 15.35 device
      pixels a character in a surface, and its grid's cell is 15 (2874
      pixels over 191 columns): 2.3% wider, a column in every 43. A document that lays
      the terminal's font out by cells loses the last column or two of a
      full line: a program's cells UI shown as text, a table whose
      columns are counted in cells, a label N cells wide for N
      characters. Found in the framework for hotty apps (gov R-23),
      whose gallery shows a screen's cells UI as text in a surface: every
      full-width line lost its last column.
      options:
      - **(a) The host sets `letter-spacing` on the root** to the cell
        less the advance. Every font inherits it, proportional ones too,
        so a document in another font would have to take it back.
      - **(b) A variable `--hotty-cell-spacing: …px`** in §8: the cell
        less the advance of `--hotty-font` at the root's size, which a
        document applies (`letter-spacing`) where it sets the terminal's
        font in columns. A document that doesn't is drawn as today.
      - **(c) The host sizes the root's font** so that its advance is
        the cell. The surface's text is then a hair smaller than the
        terminal's own, which draws each glyph at its size in its cell.
      lean: (b). It changes nothing for a document that doesn't use it,
      and the host has both numbers: hottyterm has Ghostty's advance
      before it rounds the cell, and the xterm addon has xterm's measure.
      cost:
      - §8: the variable, and a line that a document laying the
        terminal's font out in columns applies it.
      - Hosts: hotty-blitz takes the advance from its embedder, or
        measures `--hotty-font` itself; hottyterm passes Ghostty's; the
        xterm addon its measure.
      - Vectors: none; it is drawn, not told.
      - Not breaking: a new variable.

- [ ] **V6-09** A surface's CSS transitions and animations run on the host
      status: proposed, a draft; accepting it is the maintainer's; to build after plx's hotty-surf landing (the maintainer, 2026-10-31: "Record now, build after") | added: 2026-10-31
      out of the 0.6 cut (the maintainer, 2026-11-01), and proposed for 0.7
      problem: the spec says nothing of CSS transitions and animations,
      and hosts differ. A browser host runs them as any page does.
      hottyterm doesn't. Blitz computes them: Stylo keeps the document's
      animations, `BaseDocument::resolve(time)` advances them, and
      `is_animating()` says whether any is still running. hotty-blitz
      passes the clock (`surface.rs`, `resolve`) but never asks
      `is_animating()`, so it schedules no frame. A transition moves only
      when something else repaints the surface, and then it jumps. Blitz's
      site lists both as supported, which is true of the engine and not
      of this host. The maintainer, 2026-10-31: "this would be a huge
      fidelity win, offloading visual indication to the host from the
      main pipe". A program sends one change, a class or an attribute, and
      the host draws every frame between, with no bytes on the pty per
      frame. That matters most over ssh. hotty-surf's notes list both as
      known not to draw (`css-subset.md`, `blitz-gaps.md`), so its look
      uses none today.
      options:
      - **(a) Hosts run them as browsers do.** In §8, a host runs a
        surface's CSS transitions and animations, honours
        `prefers-reduced-motion` from the person's setting, and may lower
        the frame rate of a surface that isn't shown. The cells have no
        frames: a program's cells fallback shows the end state.
      - **(b) Transitions only.** Short, state-driven changes (hover,
        focus, open and close), which are most of a UI's motion, and no
        `@keyframes`. Infinite animations, a spinner for one, stay the
        program's, with a delta for each change.
      - **(c) The spec stays silent.** Each host does what its engine
        does, and a document can't count on motion.
      lean: (a). It is what Blitz already computes, and the browser host
      already does it, so (a) only brings hottyterm level. An infinite
      animation costs a raster every frame on a host, so the frame-rate
      line keeps a hidden spinner from burning a laptop's battery.
      cost:
      - §8: a paragraph, the reduced-motion line, and the cells' end
        state.
      - hotty-blitz: while `is_animating()`, schedule the next frame as
        `anim.rs` does for an animated image, and damage what moved.
        Stop when it settles. Set `prefers-reduced-motion` on Stylo's
        device from the embedder: hottyterm takes it from GTK's
        `gtk-enable-animations`.
      - hottyterm: wake its render loop for a surface's frame.
      - Measure first: what a frame costs while a hover fades and while
        a spinner turns (hotty-perf's rig), and whether Blitz's
        transitions start from the right value after a delta (Blitz
        issue #689 is noted in `resolve.rs`).
      - Vectors: none; it is drawn, not told.
      - Not breaking: a document that uses no motion is drawn as today.
