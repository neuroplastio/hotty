# hotty 0.10

Items for the version after 0.9. Nothing here is accepted or built yet.

Item template: as `tasks/0.4.md`.

## To consider

Notes, not proposals. Each one is weighed for 0.10 before anyone drafts it.

- **Rubber band and momentum on a scrolling document** (2026-11-16; the
  maintainer asked for "the rubber / spring effect when overscrolling with
  trackpads / touchscreens, similar to the browsers. Only for
  hotty-scrollable surfaces", then: "Let's shelve it for 0.9").
  - **Today:**
    - hottyterm hands a trackpad's scroll and a touch drag to a document
      that scrolls (§5.3) as precision pixel deltas (mods/ghostty 0009,
      0014).
    - A touch drag's end reaches hotty-blitz (`hotty_host_end_gesture`). A
      trackpad swipe's end and its lift velocity (GTK's scroll-end and
      `decelerate`) probably don't. Check first.
    - hotty-blitz clamps a scroll at the edge (`scroll::scroll_by`), so
      nothing stretches, and a flick has no momentum after the lift.
  - **The shape talked through (host behaviour, as scrollbars and snapping
    are):**
    - hottyterm passes the gesture's phases and its lift velocity (AppKit
      has both).
    - hotty-blitz rubber-bands past an edge during a precision gesture,
      with resistance growing with the distance, as Safari does, and
      springs back on release with a damped spring.
    - A fling coasts with friction and bounces at the edge.
    - Scroll acceleration (2026-11-16, the maintainer: "I want scroll
      acceleration when using touchscreen or trackpad (for 0.9)"): a run
      of quick swipes in one direction goes further each time, as on macOS
      and in browsers. It is the same host-side gesture model as the fling.
    - A notched wheel gets neither.
    - `overscroll-behavior: none` turns the bounce off for its box, and
      `contain` stops the chaining, as browsers do.
    - Reduced motion (V8-02) turns it off.
    - Paint only, on the frame timer that already fades scrollbars and
      settles snaps. Never a relayout.
    - xterm-addon-hotty would need its own, since the iframe can't use
      the browser's bounce for a document it scrolls itself.
  - **Open for the spec:** is a program told about overscroll? The lean is
    no: browsers fire no scroll events for the bounce. §5.3 would say so,
    so hosts agree. That is the maintainer's call.
  - **Moved to 0.10** (2026-11-22, the maintainer). First it needs **scroll
    input that says what made it.** Today hotty-blitz can't tell a wheel
    from a touchpad or a touch pan:
    - Ghostty tells hottyterm whether a scroll is `precision`, and
      mods/ghostty 0014 turns a touch drag into a precision scroll.
    - But `hotty_host_wheel` takes only pixel deltas, so the difference
      is lost.
    - Only a touch drag has phases (`hotty_host_touch`). A touchpad's
      lift probably never reaches `hotty_host_end_gesture`, so a gesture
      "ends" 150 ms after its last delta.

    The rubber band starts with an ABI change. `hotty_host_wheel` gains
    the device (wheel, touchpad, touch) and the phase (begin, move, end,
    momentum), and the end carries the lift velocity. hottyterm passes
    Ghostty's precision flag, GTK's scroll-end and `decelerate`, and
    AppKit's `phase` and `momentumPhase`. That is our own ABI, not the
    spec's. A notched wheel neither stretches nor coasts.
  - **The plan talked through:**
    - The spec text, a few sentences in §5.3, goes with the version: a
      host MAY bounce and coast, sends no scroll events for it, and
      honours `overscroll-behavior` and reduced motion.
    - The hosts' side is its own work, not gating the version: macOS
      first (AppKit makes the momentum), then Linux (our own coast).
    - The physics is unit-tested with a fake clock. The feel is tuned by
      hand against Safari, on the maintainer's trackpad and touchscreen.

- **Touch: fingers and gestures for the program** (2026-11-22, the
  maintainer: "proper touch finger / gesture events support in 0.10").
  - **Today (§9, §9.1):** a touch is a pointer with three outcomes:
    - a tap is a click;
    - a long press is a secondary press;
    - a touch on an element whose `touch-action` allows no pan drags it
      (`press`, `dragstart`, moves, drop); any other touch pans (§5.3).

    A second finger cancels a drag. The program never learns that a
    touch was a touch, sees no finger but the first, and gets no pinch,
    rotation or two-finger pan.
  - **Questions for the shape:**
    - **The model:** Pointer Events (`pointerId`, `pointerType`,
      `pressure`, one stream per finger), Touch Events (a list of touches
      per event), or gestures the host recognises (`pinch` with a scale,
      `rotate` with an angle, a multi-finger `pan`)? Browsers give raw
      fingers and leave gestures to script. A host that recognises them
      saves every program a gesture engine, as with the secondary press.
    - **Opt-in:** a `data-on` word per element (`touch`, `pinch`), with
      `touch-action` still deciding what the host pans or zooms itself.
    - **Trackpads:** macOS sends pinch and rotate from a trackpad
      (`magnify`, `rotate` events), with no touchscreen. Is a trackpad
      pinch the same `pinch`?
    - **What a surface gives up:** pinch-to-zoom is the host's today (font
      zoom, §5). An element that takes `pinch` keeps it from the host, as
      `touch-action: none` does in a browser.
    - **Hosts:**
      - hottyterm on GTK has touch sequences, GtkGestureZoom and
        GtkGestureRotate.
      - AppKit has the trackpad's gesture events.
      - xterm-addon-hotty has the browser's Pointer Events.
      - The mobile hosts (NEIO-12) make touch the main input.
      - Cells have none.
    - **Ties:** the rubber band's device and phase come from the same
      input path, so the hosts' plumbing can be shared. The other buttons
      item (0.9) settles `button` versus a meaning, which `pointerType`
      should match.
  - The maintainer's call.
