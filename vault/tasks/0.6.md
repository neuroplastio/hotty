# hotty 0.6: `scroll`

What breaks 0.5. The maintainer accepted V6-01's shape on 2026-10-25 and
asked for it drafted and held: "Draft the spec now, hold". SPEC.md on main
stays 0.5, which every implementation and the docs site pin; the wording
below is what 0.6 applies to it. 0.6 is built and released when margin's
move to one scrolling surface is approved, or other items join it. Each
item then lands in SPEC.md, SDK.md and the vectors together (AGENTS.md), on
local `hotty-0.6` branches across the stack, as 0.5 did.

Item template: as `tasks/0.4.md`.

## Accepted

- [ ] **V6-01** `scroll`: a program scrolls a surface by the steps of the scrolling keys
      status: accepted, drafted, held; accepted by the maintainer, 2026-10-25 ("`scroll` op with actions") | added: 2026-10-25
      problem: scrolling is local (§5.3). A program moves a surface only
      by focus or `reveal`, and its keys scroll it only as `data-keys`
      bindings to scroll actions (§10.2), which the host applies while the
      surface has the keyboard. A program that keeps the keyboard in the
      terminal, with a keymap of its own (modes, counts, the user's
      configuration), cannot hand its keys to the host as data, and some
      of them scroll only on a condition the host cannot know. margin, a
      reader, would move its document column to one scrolling surface, and
      needs:
      - `j` and `k` through a block taller than the window, moving focus
        to the next block only once the block's end shows. Prose has no
        element per line for `reveal` to bring into view.
      - Its own paging keys (Space, `page_down`, `ctrl+d`, `ctrl+u`), with
        counts.
      - `h` and `l` on a code block or a table that scrolls across.
      proposal: a delta op, `scroll`, whose `v` is one of §10.2's scroll
      actions. It scrolls as a key bound to that action would with focus
      on the target: the nearest element that scrolls, from the target
      outward, itself included, then outward as a gesture goes, never past
      the root. An empty `t` starts at the root.
      - Each op moves one of the host's steps, the step its key takes,
        not an amount: rows of the terminal do not map onto prose the host
        wraps, and pixels are not the program's unit. A count is as many
        ops, and n ops move n steps even while a smooth scroll still
        moves.
      - It moves as the key does on that host, smooth or not. It stops a
        gesture's momentum, and a gesture takes over from it.
      - Where nothing can move, or along an axis the document does not
        scroll, it does nothing and is no error. The program hears where
        things came to rest from `view` (§9.5), as after any scroll.
      - It works whether the surface has the keyboard or not, moves
        neither focus nor the keyboard, and sends no event of its own.
      - A `v` that is not a scroll action is `EINVAL`.
      cost: one op for every host. Both already find the box and take the
      step for scrolling keys (hotty-blitz `scroll.rs`, the addon's
      `scrollBox`), so the op calls that code from a delta. Each SDK adds
      `ScrollOp` and `Scroll`, and the test hosts move offsets as they do
      for `reveal`. A 0.5 program meets a 0.6 host at `EVERSION`, as at
      every minor.
      legs (local `hotty-0.6` branches, pushed when all have landed):
      - [x] hotty: the wording below, in the vault (2026-10-25)
      - [ ] hotty: SPEC §5.3, §6.1, §10.2, §16, App. B; SDK.md; vectors;
        Python client; CHANGES; docs
      - [ ] hotty-go (+ hottytest), hotty-ts, hotty-lua, hotty-rs
      - [ ] hotty-blitz, xterm-addon-hotty, hottyterm re-pin
      - [ ] plx relay, margin, web/hotty and the docs site's pins, which
        follow the release
      settle while building: a multiplexer that keeps deltas for the
      terminal that attaches (§3.6 `ENOTERM`) would replay a scroll the
      user never saw; `reveal` already has the same question. margin's
      lean (2026-10-25): replay neither, so a late terminal starts at the
      top; margin brings its focused block into view again after that
      terminal's first `view`.

### V6-01: the wording

**§5.3**, the bullet *Scrolling is local*:

> - Scrolling is local: the program hears of it only where it asks, which
>   elements are in view (§9.5), and moves it only by focus (§10.1), by
>   bringing an element into view (`reveal`, §6.1), or by the steps a
>   scrolling key takes (`scroll`, §6.1). A delta keeps the offsets
>   (§6.2), and a new document starts at the top left.

**§6.1**, a row after `reveal`:

> | `scroll` | a scroll action (§10.2) | scroll as a key bound to the action would, from the target (below) |

**§6.1**, *Checked first*: `t` is missing or empty where the op needs one
"(every op but `morph`, for which an empty `t` is none, and `scroll`, for
which it is the root)", and the last case reads "or `reveal` has a `v`
other than `start` or `end`, or `scroll` one that is not a scroll action
(§10.2)".

**§6.1**, a bullet after *Reveal*:

> - **Scroll** changes no node. It scrolls as a key bound to its `v` would
>   with focus on the target (§10.2, *Scrolling keys*), whether the surface
>   has the keyboard or not: the nearest element that scrolls, from the
>   target outward, itself included, or the root when `t` is empty. Where
>   that cannot move that way, it goes outward as a gesture does (§5.3), as
>   far as `overscroll-behavior` lets it, and never past the root.
>   - **One step** of the host's for each op, the one the action's key
>     takes, so a program scrolls by a count with as many ops. A host that
>     animates the key animates the op, and each op starts from where the
>     one before it was going, not from where the box is drawn, so n ops
>     move n steps. An op stops the momentum of a gesture, and a gesture
>     takes over from an op still moving.
>   - **Nothing to move** is no error. Where nothing it may reach can move,
>     along an axis the document does not scroll (§5.1 `scroll`), and in a
>     surface not placed, it does nothing.
>   - Like `reveal`, it moves neither focus nor the keyboard (§10), and
>     sends no event of its own: elements that report whether they are in
>     view report it once the scroll comes to rest (§9.5).

**§10.2**, *Scrolling keys*, after the example of `data-keys`:

> A program that keeps the keyboard, or scrolls only on a condition of its
> own, scrolls by the same steps with the `scroll` op (§6.1).

**§16**: the vectors check "`reveal`, `scroll` and `view`".

**Appendix B**, after *Why `reveal` and `view`*:

> - **Why a `scroll` op.** Scrolling keys (§10.2) serve a program that can
>   hand its keys to the host as data. One that keeps the keyboard in the
>   terminal, with a keymap of its own, its modes, counts and the user's
>   configuration, cannot, and some of its keys scroll only on a condition
>   of its own: `j` in a reader scrolls through a block taller than the
>   window, and moves to the next block once the block's end shows. Prose
>   has no element per line for `reveal` to bring into view.
>   - **The host's steps, not an amount.** The host wraps the prose, so
>     rows of the terminal do not map onto its lines, and pixels are not
>     the program's unit. The steps are those the user's own keys take,
>     so the program's keys and the surface's agree.
>   - **From a target, as a key from focus,** so one rule says what
>     scrolls: a code block that scrolls across takes `h` and `l`, and the
>     document around it `j` and `k`.
>   - **Still local.** Gestures stay the host's, the program hears where a
>     scroll came to rest only from `view`, and an op that can move
>     nothing does nothing, as a key does.

**SDK.md**:
- *delta ops* gains `scroll`.
- The op builders gain `ScrollOp`: op `scroll`, parameters target
  (empty: the root) and action.
- The messages gain `Scroll`: `Delta` with one op, `ScrollOp`, where
  action is a scroll action (SPEC.md §6.1); parameters surface, target,
  action; level 2.
- The key order: `t` unless the target is empty, and `v` always.
- The names table: `hotty.OpScroll` and `Scroll` in Go, `scroll_op` and
  `scroll` in Python, `scrollOp` and `scroll` in TypeScript.

**Vectors**: build `ScrollOp` and `Scroll`, with a target and without.
Hosts:
- `EINVAL` for a `v` that is none, `start` or `down`;
- `ENOTARGET` with the id as detail;
- a surface not placed answers ok;
- in a long document, `scroll-end` then `view` with `end: true`, and
  `scroll-start` back;
- `scroll-down` from an element that cannot move reaches the root;
- along x in a document of `scroll=y`, nothing.

A host chooses its steps, so the vectors check which box moved and what
`view` reports, not by how much, except at the ends.

- [ ] **V6-02** A text field may give the program `tab`
      status: accepted; accepted by the maintainer, 2026-10-30 ("prefer
      browser-like model where default behavior is standard, but the app
      can still override it") | added: 2026-10-29
      problem: a command palette or a picker completes what was typed on
      Tab, as shells and fuzzy finders do, and its users expect it. In
      the cells it can. On a surface it cannot: Tab moves focus, and a
      host ignores a `data-keys` binding of `tab` (§10.2), so the program
      never hears it from its field. A palette whose field is its only
      focusable element hands the keyboard back to the terminal on Tab
      instead. The program has to pick another key, one users of its
      cells version don't know.
      proposal: a host honours `tab=program` in a text field's keymap
      (§10.2), and only there. `shift+tab` and `escape` keep their
      meaning everywhere, and `tab` keeps it on every other element.
      - The field gives the program `tab`, which reaches it as any key a
        field gives does. The program decides: it completes with
        `a=field` (§6.4), or moves focus itself with `a=focus`.
      - Shift+Tab still moves focus back, and Escape still reaches the
        program, so a user always has a way out of the field.
      - Only a text field: a button or a list has no reason to keep Tab,
        and focus order stays the host's.
      cost:
      - §10.2: "bindings of `tab`, `shift+tab` and `escape`" becomes
        "bindings of `shift+tab` and `escape`, and of `tab` to anything
        but `program` or outside a text field".
      - SDK.md: Keymap and Resolve read the binding.
      - Vectors: a field with `tab=program` gives the program `tab`; one
        without moves focus.
      - Forward Tab past such a field takes Shift+Tab or a key the
        program binds: an accessibility cost a program takes on by
        binding it.
      - Not breaking: a binding hosts ignore today starts to hold.

- [ ] **V6-03** Enter commits a text field, in a form or not
      status: accepted; accepted by the maintainer, 2026-10-30 ("Yes, like
      browsers") | added: 2026-10-30
      problem: §9's `change` comes for a text control "when the change is
      committed (focus leaves it, including when the surface loses the
      keyboard)", and `submit` for "Enter in a text field" of a form. It
      doesn't say whether Enter commits a field that is in no form, and
      the stack answers both ways:
      - hotty-blitz commits on Enter, then submits where there is a form:
        its `submit` action runs `finish_change` first
        (`crates/hotty-blitz/src/surface.rs`, the `"submit"` arm), so a
        lone field sends `change` on Enter.
      - hottytest commits and submits only inside a form
        (hotty-go `hottytest/keys.go`, `case a == hotty.Submit`), so a
        lone field sends nothing on Enter, and `change` only on blur.
      - Browsers fire `change` on Enter in a text `input` whose value
        changed, with or without a form.
      A program tested on hottytest and run on hottyterm sees different
      events. The framework for hotty apps (gov R-23, NEIO-15) met it:
      its fields now commit on Enter themselves (the runtime takes Enter
      for a field with a change handler) and on `change`, so it depends
      on neither reading.
      proposal: Enter commits. §9's `change` row reads "when the change is
      committed: Enter in a text `input`, or focus leaving it (including
      when the surface loses the keyboard)". Enter in a form's field then
      commits and submits, as both hosts do today.
      cost:
      - §9: the `change` row's wording.
      - hottytest: commit on `submit` outside a form too.
      - Vectors: Enter in a lone changed field sends `change`; in a form,
        `change` then `submit`.
      - Not breaking for a program: what hottyterm sends already.

- [ ] **V6-04** A scroll comes to rest on a row: CSS scroll snapping
      status: accepted; accepted by the maintainer, 2026-10-30 | added: 2026-10-30
      problem: a document laid out in rows of cells (a list, a file's
      lines, one row each) scrolls by the host's steps, which are not
      rows. hotty-blitz moves 40 CSS px for an arrow and 7/8 of the box
      for a page. After Page Down a pane shows half a row at its top, and
      at a cell height that doesn't divide 40 px an arrow stops between
      rows too. Seen in a two-pane file preview whose panes the host
      scrolls by the wheel and the keys: at 20 px rows an arrow is two
      rows, and a page 29¾. A document can't ask for row steps. V6-01's
      `scroll` op moves by the same steps, so it inherits this.
      proposal: hosts honour CSS Scroll Snap on an element that scrolls
      (§5.3): `scroll-snap-type`, `scroll-snap-align` and
      `scroll-padding`. A program that wants whole rows marks them
      `scroll-snap-align: start` under `scroll-snap-type: y mandatory`, and
      every scroll then comes to rest on one, as in a browser: a key's
      step, a page, the wheel, a `reveal` and V6-01's `scroll`. The
      host's own steps stay as they are; snapping is where they end.
      - Browser-like: a standard property with its standard meaning, so a
        document a browser draws scrolls the same, and nothing new is
        named.
      - Not chosen: steps of one cell row by default. It changes every
        document, prose included, and a browser doesn't step so.
      cost:
      - §5.3: the three properties, in the list of CSS that applies to
        scrolling.
      - hotty-blitz: Blitz has no scroll snapping; a patch on its pinned
        Blitz that picks the snap position after each scroll, mandatory
        and proximity.
      - The xterm addon: a browser has it already.
      - Vectors: a list of 20 px rows under `y mandatory`, after Page
        Down in a box of 30.5 rows, shows a whole row at its top.
      - Not breaking: a document without the properties scrolls as
        today.

- [ ] **V6-05** A keymap may give a key back to the host
      status: accepted; accepted by the maintainer, 2026-10-30 | added: 2026-10-30
      problem: §10.2 merges `data-keys` from the root down. A key an
      element gives the program holds for everything inside it, and no
      action takes it back.
      - A list that binds Space to the program, to toggle its rows, takes
        Space from a button inside it, which Space should press, and
        from a text field inside it, which should type a space. A
        framework that writes such a keymap has to put stand-ins on the
        button (`space=scroll-page-down`, so Space at least scrolls) and
        has no stand-in at all for typing.
      - The same holds for every key a field types and an ancestor binds:
        a letter that a list uses as a shortcut can't be typed in a field
        inside it.
      proposal: an action `default`. `key=default` in an element's keymap
      gives that key back to the host's own meaning for that element and
      what is inside it, as if no element above had bound it: Space
      presses a button and types in a field, an arrow scrolls or moves a
      caret. It is an override like any other, and the nearest binding
      still wins.
      - Browser-like: the default action is the browser's, and a page
        gives it back by not calling `preventDefault` in the inner
        element's handler. `default` is that, as data.
      cost:
      - §10.2: the action, beside `program` and the scroll actions.
      - SDK.md: Keymap and Resolve read it.
      - Hosts: the keymap's resolution stops at a `default` and does what
        it would with no keymap.
      - Vectors: a button inside a list that binds Space, with and
        without `space=default`; a field likewise, with a letter.
      - Not breaking: no keymap has the action today.

## Proposed

- [ ] **V6-06** A backdrop: a placement drawn under the cells
      status: proposed, a draft; accepting it is the maintainer's | added: 2026-10-31
      problem: every placement is above the cells, whatever its `z`
      (§5.2). A program that shows several terminals at once, as a
      multiplexer does with its panes, can only separate them with cells:
      box-drawing lines a cell wide, or a blank gutter. What makes a
      native window read as one is under the text: each terminal a
      rounded card in its own background, on a darker canvas, with a few
      pixels of gutter, and the focused card ringed. A surface above the
      cells can't do it without hiding the text, and a terminal's text
      can't move into a surface.
      what kitty graphics already does: a kitty image placed with a z
      below −1,073,741,824 (INT32_MIN/2) is drawn under the cells'
      backgrounds. A cell with the default background is transparent
      over it, and a cell with any other background covers it. Ghostty
      draws such images in a layer of their own (`kitty_below_bg`), after
      the window's background and before the cells'. So most of this is
      there today for a program that speaks kitty graphics. What it lacks:
      - It rasterises the image itself, so it has to know the cell size
        in device pixels and draw the image again on a zoom, a display
        with another density, or a change of font. A surface is laid out
        by the host at the cells' size, in the theme's colours
        (`--hotty-*`, §8), and drawn again without the program (§5.3).
      - It sends every frame whole, where a surface sends deltas (§6).
      - It needs kitty graphics. The xterm addon has none, and a
        multiplexer would have to relay them.
      - Nothing says a host has it, short of drawing and looking.
      proposal: a placement key `b`, a backdrop. With `b=1` the
      placement is drawn under the cells, as kitty graphics draws images
      below the backgrounds: a cell with the default background is
      transparent over it, and a cell with any other background, the
      cursor and the text cover it.
      - **Stacking:** backdrops are under every cell and under every
        placement without `b`. Among themselves they stack by `z` and
        creation, as placements do (§5.2).
      - **The placement's, not the surface's:** like `z`, `b` belongs to
        the placement. Placing the surface again without `b` puts it
        back above the cells.
      - **No input:** a backdrop takes no pointer, and the pointer
        reaches what is above it, the cells or another window. It never
        has the keyboard. `a=focus` on a surface whose placement is a
        backdrop is `EINVAL`, and no click focuses it. Its hover, press
        and fit events (`v`, `p`, `f`) hold as on any placement,
        except that a backdrop sees no pointer, so `p` and `v` send
        nothing.
      - **The feature `backdrop`** (§4): a host lists it when it draws
        backdrops. A host without it ignores `b` as an unknown key
        (§15) and draws the surface above the cells, over the text. So
        a program **MUST** check `features` before placing a backdrop,
        and falls back to cells (borders, gutters) without it.
      - **The window's edges:** a host may keep room round the cells
        that no cell covers: the padding it is set to keep, and what is
        left of the window where it isn't a whole number of cells. A
        backdrop that reaches an edge of the screen goes on to the
        window's edge there. The host draws the backdrop's outermost
        pixels across that room: the edge row or column drawn out, and
        the corner pixel in a corner. So no part of the window shows the
        terminal's own background unless the backdrop or a cell paints
        it, and a program needs to know nothing of the padding. A
        backdrop that reaches no edge stops at its cells. A cell that
        paints its background still covers the room beside it where the
        host extends edge cells into the padding, since cells are above
        backdrops. Placing the backdrop in window pixels instead would
        make the program learn the padding and the window's size, which
        hotty keeps from it (placements are in cells, §5.2).
      - The rest is a placement as before: the window, the cursor
        (`C=1`), scrolling with the screen, and deletion.
      A program that cards its panes places one backdrop the size of
      the screen, at the top left with `C=1`: the canvas, and a card per
      pane in the pane's background, reaching half a gutter past the
      pane's cells, with a ring on the focused card. It leaves the panes'
      cells on the default background, and redraws the backdrop (a delta)
      when a pane moves, splits or takes the focus.
      cost:
      - §5.2: the key, the stacking and the input rules above, and "every
        placement is above the cells" becomes "every placement without
        `b`". §4: the feature. §15: nothing new.
      - SDK.md: Placement gains Backdrop, written as `b=1`, and the
        features table its row.
      - hotty-blitz: parses `b`, passes it to the embedder's place
        callback (a C ABI change), lists the feature where the embedder
        says it draws backdrops, and refuses `a=focus` on a backdrop.
      - hottyterm: surfaces are already kitty images, so a backdrop is
        one with a kitty z below INT32_MIN/2, left out of the pointer's
        hit test: about 30 lines in `hotty.zig`. The edges are Ghostty's
        renderer's: a strip of the edge pixels past each edge a backdrop
        reaches, about 100 lines with the test.
      - The xterm addon: a layer under xterm's canvas, with the default
        background transparent there, and as large as the element the
        terminal is in, padding included. The most work of the three.
      - Vectors: `b=1` round-trips in the builders. A host with the
        feature lets a press over a backdrop reach the cells, and
        answers `a=focus` on one with `EINVAL`.
      - Not breaking: a 0.5 host ignores `b` (§15), which is why the
        feature is needed.
      prototype: hottyterm's `backdrop` branch, patches 0047 to 0049
      (`mods/ghostty/backdrop-placements.md`, `backdrop-bleed.md`,
      `backdrop-feature.md`). It reads `b=1` in hottyterm before
      hotty-blitz does. It lists the feature through a shim that adds it
      to the capabilities as they pass to the program, until hotty-blitz
      lists it. The demo, `scripts/backdrop-demo.py` there, is three
      panes of text in cells on one backdrop of rounded cards, with a
      gutter between them and a ring on the focused card. It checks the
      features first, and draws the same panes with box-drawing borders
      on a host without `backdrop`, or with `--boxes`. The gutter is a
      row tall and two columns wide, which leaves the text about 7 CSS px
      of padding at a card's sides at 1.6, closer to a native window's;
      one column (`--gutter 1`) leaves about 3. Before the edges' rule,
      a 2874x1845 window at 1.6 showed the terminal's background in a
      strip 30 pixels tall under the grid and 9 wide beside it.

- [ ] **V6-07** The default sheet rings controls on focus, not what holds them
      status: proposed, a draft; accepting it is the maintainer's | added: 2026-10-31
      problem: the host stylesheet (§8) gives every `:focus-visible`
      element `outline: 1px solid var(--hotty-accent)`. A document that
      focuses a container, to take keys or to scroll by them (an element
      with `tabindex`, a scrolling region, a list, the body), gets a ring
      round all of it, and a click on a scrolling page rings the whole
      surface. Every document has to know the default draws it there and
      take it back (`outline: 0`), which a framework's sheet does, but a
      small program's doesn't.
      options:
      - **(a) Drop the rule.** Focus shows only as the document's sheet
        says. A document with no sheet then shows no focus at all, which
        leaves a keyboard user lost.
      - **(b) Ring the controls only:**
        `:is(a[href], button, input, select, textarea, summary):focus-visible`.
        A container that takes the focus shows nothing by default, and a
        bare document's controls keep the ring.
      lean: (b). The ring is the default's way to show which control has
      the keyboard; it was never meant for a page, a pane or a list, and
      a document that wants one there says so.
      cost:
      - §8: one selector, and a line under it that a focused container
        has no ring by default.
      - Hosts: hotty-blitz's copy of the sheet, and the xterm addon's.
      - Vectors: a focused element with `tabindex` and no ring, beside a
        focused button with one.
      - Not breaking: what changes is drawn, never what a program is
        told. A program that wanted the ring on a container adds it.
